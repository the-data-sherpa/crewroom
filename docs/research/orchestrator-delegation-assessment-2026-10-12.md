# Orchestrator-style delegation assessment

2026-10-12 · [FOR-15](https://linear.app/forgeinnovations/issue/FOR-15/assess-orchestrator-style-task-delegation-for-crewroom). Static research; the operator subsequently accepted the bounded recommendation in [FOR-16](https://linear.app/forgeinnovations/issue/FOR-16/record-accepted-delegation-scope-for-mh5-and-mh6). No runtime or installation changes.

**Accepted direction:** adopt the interaction pattern in MH5/MH6: describe an outcome, refine the plan, delegate named responsibilities, inspect progress and route blockers through the existing run coordinator. Keep Crewroom's service authoritative, one executing coding ticket and explicit Resume for PR feedback. The [accepted plan](../multi-harness-plan.md#accepted-delegation-decisions) owns implementation scope. A persistent project planner, parallel coding tickets and automatic feedback admission remain possible later expansions outside this MVP.

## Evidence boundary

The [website](https://orchestrator.inc/) markets a main agent per project, isolated workers and automatic PR feedback. The [manual](https://docs.orchestrator.inc/) identifies stable **v0.13.3, 2026-10-01**; it warns that `main` differs. Source findings below are pinned to [95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e](https://github.com/OrchestratorInc/agent-orchestrator/commit/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e), committed 2026-10-12. This was static inspection, not an installed-product trial or verified live delivery.

## What Orchestrator actually supplies

**Project planner above task workers.** The [README](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/README.md) describes a persistent project conversation covering goals, priorities, decisions and live worker state. Workers own implementation and PRs. Source [reuses an existing active orchestrator](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/service/session/service.go#L304-L347) under a project lock. This is broader than Crewroom's coordinator for an admitted run.

**Delegation is principally instructions plus commands.** The [orchestrator prompt](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/session_manager/prompt.go#L197-L266) directs it to inspect ownership, plan complex work, reuse or spawn workers, send context and monitor results. It prohibits implementation through harness-native subagents and directs all communication through AO. Those instructions do not establish a machine-enforced decomposition or accepted-plan gate. The [New task service](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/service/session/delegation.go#L59-L133) directly creates a worker; no orchestrator is required. A concrete service guard [rejects orchestrator PR claims](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/service/session/claim_pr.go#L62-L78). I did not establish a universal filesystem-write prohibition for orchestrators.

**Isolation and selection.** [Parallel-work documentation](https://docs.orchestrator.inc/guides/parallel-issues/) assigns each Git worker a branch/worktree, conversation and controller. Independent tasks can run concurrently; remote pushes, PRs and CI remain shared repository effects. [Role settings](https://docs.orchestrator.inc/guides/per-role-agents/) separate worker/orchestrator harness and model defaults. The delegation API accepts harness, model, effort and permission overrides. This is harness-aware selection, not evidence of Crewroom's intended model-first equivalence and routing policy.

**Messages and visibility.** The [dashboard](https://docs.orchestrator.inc/dashboard/) derives displayed status from saved activity, controller and PR facts and exposes worker Chat/terminal, changes and reviews. Source provides [durable worker reports](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/service/report/coordinator.go#L123-L203), routed to the active project orchestrator through claimed batches and acknowledged delivery. Its [send command](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/skillassets/using-ao/commands/send.md) documents durable steering handles and recovery; delivery acknowledgement does not prove the agent applied guidance. These patterns fit Crewroom's observable external-message contract without introducing AO's transport.

**Feedback, review and merge.** Current [reaction code](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/lifecycle/reactions.go#L139-L283) gates CI/review injection on policy flags and session state, deduplicates messages, and handles merge conflicts separately. Thus the website's feedback promise has configuration and state qualifications. [Review planning](https://github.com/OrchestratorInc/agent-orchestrator/blob/95dd4d712d5b6026cc00d59fd0dd63aea5c4e66e/backend/internal/review/planner.go#L37-L85) keys results to PR/head. The [review guide](https://docs.orchestrator.inc/guides/review-loop/) describes separate reviewer agents, optional automatic review and explicit merge; an AO verdict is not repository-host approval. This does not establish Crewroom's complete acceptance-coverage/check-evidence gate.

**Tracker limit.** The [current introduction](https://docs.orchestrator.inc/#supported-agents) explicitly supports GitHub/GitLab issue intake, read-only toward trackers, and excludes Linear and legacy Node plugins. [Architecture](https://docs.orchestrator.inc/architecture/#services-and-adapters) requires daemon and project opt-in. Do not infer current Linear support from older material. Crewroom's Linear development tracker and Jira product integration remain distinct; adopting AO would not supply either synchronization contract.

## Smallest compatible Crewroom adaptation

The accepted [product contract](../product.md), [architecture](../architecture.md), [reuse assessment](omp-team-reuse-assessment.md) and [MH plan](../multi-harness-plan.md) already supply most foundations. Reuse them:

1. **MH5:** record named work packages, dependencies, expected outputs and acceptance criteria in the accepted implementation plan. Reuse a current plan; grill only missing decisions. Distinguish proposed assignments, queued work and running processes.
2. **MH6:** let the existing per-run coordinator assign those responsibilities to the writer, active navigator and staged UI/documentation specialists. Freeze role/model/route and work scope in assignment briefs. Keep one coding ticket, at most three specialists, one writer per worktree, explicit writer transfer and a separate final reviewer.
3. **Supervision:** present assignment ownership, meaningful reports, artifacts and blockers in the existing agent grid/coordinator conversation. Preserve external mail, independently observable processes, interruption recovery and revision-bound evidence across OMP, Codex and Claude Code.
4. **Feedback:** show CI/review changes and route admitted rework to the owning run. Preserve operator Resume, renewed checks/review and human merge. Observation alone must not admit new execution.

The operator accepted this bounded approach on 2026-10-12 for later MH5/MH6 implementation. Validate it through the already-required planned/unplanned intake, backend/UI pair and interruption scenarios, retaining the existing queue and PR-feedback controls. Implementation remains in Backlog.

## Possible later expansions

A durable project-wide orchestrator would need its own scope, memory, lifecycle, queue authority and relationship to run coordinators. Multiple simultaneous coding tickets would need capacity, dependency/merge ordering, shared-resource and ownership tests. Automatic PR-feedback admission would change operator control and need explicit policy and bounded recovery. The operator chose to retain the current contracts for this MVP and revisit expansion only if needed. Adopting AO itself would add a second workflow owner and a separate Go/SQLite lifecycle; no integration is included. S9 remains after MVP.
