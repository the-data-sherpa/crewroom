# Pi Durable and Crewroom assessment

Tracked by **FOR-19**. Inspected 2026-10-17. This is a static source, design, and test inspection; upstream tests and live providers were not run, dependencies were not installed, and existing runtimes were not changed.

**Recommendation:** retain Crewroom's workflow and multi-harness architecture. Pi Durable offers useful task/checkpoint and replay-safety abstractions, but adopting it does not replace independent-process supervision, external-effect reconciliation or revision-bound delivery evidence. The most useful next investigation is whether explicit replay classification can safely reduce unnecessary native recovery holds.

## Pi Durable

**It is a programmable agent harness that owns the model/tool loop.** Its unit of work is a conversation with a model configuration, transcript, durable tasks, and typed documents. Generation resolves a `pi-ai` model and calls `models.streamSimple()`; this is not an adapter that launches the native Codex or Claude Code harness. Model-provider support for OpenAI/Anthropic therefore does not establish compatibility with Crewroom's native process/session contracts. That compatibility would need a separate integration. [Generation implementation](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/harness/generation.ts#L205).

**The strongest reusable idea is one atomic persistence boundary for task state and conversation state.** A commit can append transcript entries, edit documents, and create tasks together; publication follows successful storage commit. Tasks persist explicit phase checkpoints, waits, and outcomes. External process, network, model, and human effects occur outside that transaction, so an external effect and its recorded result can still be separated by a crash. This reduces local bookkeeping without providing a transaction across external systems. [Session transaction contract](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/docs/spec.md#L1602), [transaction implementation](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/session/transaction.ts).

**Recovery distinguishes repeatable work from uncertain effects.** A tool's arguments and replay policy are committed before execution. On recovery it runs again only if both the stored policy and current declaration say `safe`; omitted policy is unsafe. Otherwise Durable records an interrupted tool result with retained partial output, which the model can respond to. This is not a global recovery hold requiring operator reconciliation. A model request interrupted midstream is resent, with a committed partial answer recorded as aborted. `requestId` deduplicates submission admission within a conversation; it does not make arbitrary tool effects exactly once. Applications must supply effect-specific idempotency or reconciliation. The upstream transfer test makes this explicit by using a fake external service keyed by a stable request ID. [Tool implementation](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/harness/tool.ts#L117), [submission implementation](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/harness/submissions.ts), [idempotent-effect recovery test](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/test/harness-tasks-recovery.test.ts#L47).

**Steering has explicit delivery boundaries.** Busy inputs persist in an inbox: steering joins after the current tool round; follow-ups start after the run answers. Submissions distinguish queued, placed, answered, and unanswered states. Failed runs leave queued inputs pending. Cancelling a wait does not cancel work; cancelling a queued submission withdraws it. These states would support honest UI receipts, but placement alone does not prove the model followed an instruction. [Busy-conversation API](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/README.md#L408), [inbox implementation](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/harness/inbox.ts).

**Child ownership is a lifecycle mechanism, not process isolation.** Tasks and conversations form an ownership tree; cancellation drains foreground descendants before their owner finishes. Background work survives ordinary conversation abort unless explicitly included. A subagent is assembled from an owned conversation and tool. The default scheduler executes task handlers in the host JavaScript process. Non-cooperative handlers can prevent graceful close; forced termination requires host-supplied worker/process isolation. This does not satisfy Crewroom's independently observable specialist-process contract by itself. [Scheduler](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/harness/scheduler.ts), [child-task example](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/test/examples/24-child-tasks.ts), [forced-termination boundary](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/docs/spec.md#L3575).

**Storage has a single-owner contract and qualified durability.** Backends include memory, SQLite, and JSONL. One process owns a storage; the package does not provide cross-process ownership locking. Node SQLite commits use SQL transactions, WAL, and `synchronous=NORMAL`, so the newest acknowledged transactions can be lost on power/host failure. JSONL defaults to no `fsync`; even its `fsync` mode does not flush the main marker on every ordinary publication. Use precise process-crash claims, not unconditional data-loss guarantees. [Storage contract](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/README.md#L662), [Node SQLite adapter](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/src/storage/sqlite/node.ts#L145), [JSONL publication contract](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/docs/spec.md#L5159).

**The implementation is substantial but explicitly experimental.** README warns that APIs may change without notice. The October 12 release includes breaking tool/result and storage-error changes; October 15 fixes model context ordering after compaction. Inspected tests cover SQLite reopen, safe/unsafe replay, partial-generation recovery, abort stages, request deduplication, task migration, and nested calls. They are useful test designs, not freshly executed evidence or proof of production reliability. [Changelog](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/CHANGELOG.md), [tool recovery tests](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/test/harness-tools-recovery.test.ts), [generation recovery tests](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/test/harness-generation-recovery.test.ts), [nested-call restart tests](https://github.com/earendil-works/pi/blob/8efd314fa3d3232ce197d8d7a6a5660530b9d83e/packages/durable/test/harness-nested-tools-restart.test.ts).

## Comparison with implemented Crewroom

**Assessment:** Pi Durable overlaps with Crewroom's execution plumbing, especially persistence, steering and recovery. It supplies a reusable abstraction for a model loop the application owns. Crewroom supplies the software-delivery workflow and supervises independent harnesses. Replacing Crewroom's workflow service would discard responsibilities Pi Durable does not supply out of the box.

Crewroom source inspected: `f79a8d791c22705c21fd7cad2c2338b90f597e28` on `main`. The accepted [product direction](../product.md), [architecture](../architecture.md), [current status](../status.md) and [retired OMP reuse assessment](omp-team-reuse-assessment.md) remain authoritative.

| Concern | Pi Durable | Crewroom today |
| --- | --- | --- |
| Durable state | One commit boundary for conversation entries, tasks, submissions and application documents | Transactional SQLite workflow state, plus separate durable host/runner journals, native histories and external Mail receipts; cross-boundary reconciliation remains necessary |
| Agent execution | Owns the model/tool loop through Pi AI; conversations share a harness unless the host separates them | Separately supervised OMP, Codex app-server and Claude Code processes behind one runner interface |
| Interruption recovery | Explicit task phases; safe tools can replay, unsafe interrupted calls produce error results | Resume retained sessions when receipts/history agree; hold uncertain input, effects, ownership or native-history transformations |
| Steering | Durable queued/steered submissions and stable request IDs | Stored, dispatched, runner-received and applied/rejected observations, with external agent messages |
| Concurrent work | Task ownership, child conversations, background tasks, forks and cancellation | Accepted work packages, writer/navigator pairs, staged specialists, explicit writer transfer and one coding slot |
| Completion | A conversation/submission/task can settle | Readiness additionally requires the exact candidate, current requirements, required checks, independent review and resolved package obligations |
| Instruction changes | Registry reload and conversation configuration can change later requests | Admitted role/model/route/instruction snapshots are retained; learning adoption and comparisons are explicit |
| Delivery product | Application-specific tools and policy must be supplied | Jira intake/writeback, accepted plans, repository ownership, PR reconciliation, human review/merge and native supervision UI |

### Where Pi Durable could improve our design

1. **Explicit replay classification.** Crewroom's native contracts currently hold even ordinary tool argument/read failures whose lack of effect has not been classified. A typed distinction between known no-effect failure, replay-safe reads, completed keyed effects and uncertain effects could reduce avoidable stops. Pi's saved-and-current replay-policy check is useful precedent. This would require extending native receipt reconciliation, not merely retrying the call. Keep unknown writes held. See the [Codex limits](../testing/mh2-runtime-acceptance.md#authority-accounting-and-recovery) and [Claude recovery contract](../testing/mh3-runtime-acceptance.md#tools-inputs-and-recovery).
2. **More uniform durable task phases.** Pi puts checkpoints, waits, cancellation and child ownership under one task API. Crewroom already persists these facts across its scheduler, supervisor, tools and provider actions, but their implementation is specialized by subsystem. A narrower shared contract might reduce repeated crash-boundary reasoning. That is a design opportunity, not evidence that the existing mechanisms are broken or that a rewrite would be smaller.
3. **Conversation history as a first-class durable object.** Forking, compaction and atomic transcript/application-state updates are useful when owning the model loop. Crewroom cannot get those guarantees for Codex/Claude internals simply by wrapping them in Pi. Its conservative native-history holds would remain unless the native integration contract changed.
4. **Inspect the task ownership graph.** Pi's explicit foreground/background ownership could inform clearer recovery diagnostics. A finished parent must not hide unfinished owned work. Crewroom's existing comparison cancellation/finalization evidence already demonstrates why that distinction matters; see [FOR-14 status and evidence](../status.md).

### Recommendation and bounded next step

Keep Crewroom's Rust service, native workbench, external Mail and existing runner interfaces. Borrow the task/replay concepts before considering a dependency. Pi Durable's unified storage does not make a network write atomic: a crash after PR creation but before saving its receipt still needs provider readback. Crewroom already implements that reconciliation.

If a Pi-specific capability becomes desirable, the compatible integration is an additional runner adapter, with one externally supervised Pi process and private storage per assignment, Crewroom-authorized tools, external Mail, and Crewroom retaining workflow authority. This is an architectural inference, not a tested adapter. It adds JavaScript hosting and another evolving runtime; model-provider access through Pi AI is not equivalent to Crewroom's native Codex/Claude harness contracts.

A useful first spike would characterize replay classification in isolated fixtures: crash before effect, after effect but before receipt, after receipt but before native delivery, and during Pause/Cancel. Prove a known-safe read can recover while an unknown write stays held; retain original logical IDs and prevent a replacement writer until old processes and tool descendants are stopped. For an actual Pi adapter, also prove addressed external Mail, stable assignment settings, active-time accounting, and unchanged candidate/review gates. Start recovery/steering verification from the [versioned feature map](../testing/feature-map/README.md). No spike, adapter or roadmap expansion is accepted by this research.
