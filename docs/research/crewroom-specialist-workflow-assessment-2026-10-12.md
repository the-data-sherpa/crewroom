## Finding

**Crewroom already implements most of the requested factory's execution machinery.** The remaining mismatch is primarily admission and team policy: automatically divert an unplanned job into scoping, define the requested programming partnership, and require appropriate UI/documentation coverage. This is a better starting point for this particular workflow than discarding it solely to obtain a generic orchestrator. That recommendation is an engineering inference from the mechanisms below, not a measured product ranking.

The TypeScript service is retained compatibility/domain evidence: `dev` and `start` launch native Rust, while browser commands are explicitly `*:legacy`. Current native main preserves the same queue/role constraints and adds model-job settings and advisory playbooks. [Local package scripts](/home/crewroom/Projects/crewroom/package.json:9), [current status](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/docs/status.md#L9), [playbooks](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-core/src/playbooks.rs#L1).

## Specific gaps against the requested experience

**No-plan → Grill is not implemented as a gate.** Explore/Grill is explicitly optional. Coding queue admission checks repository, brief, criteria and requirement freshness, with no implementation-plan artifact/approval check. Refinement is a separate coordinator-only conversation; its prompt explicitly forbids repository access and specialist/coding tools. Therefore it can challenge supplied requirements, but is not currently a code-aware planning team automatically entered when a plan is absent. [Product contract](/home/crewroom/Projects/crewroom/docs/product.md:23), [current native admission](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-core/src/store.rs#L430), [refinement prompt](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/supervisor/workflow/configuration.rs#L553).

**Codex + Opus pairing needs a precise contract.** Roles can override model/effort or inherit configured `code`, `judgment`, `review`, and `fast` model jobs; this is deterministic configuration, not semantic model routing. Execution uses OMP with selected provider models, not separate Codex CLI and Claude Code harnesses. The inspected defaults and coordinator/team protocols contain no driver/navigator, alternating-turn or pair-signoff contract. [Model resolution](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/model_policy.rs#L28), [OMP invocation](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/supervisor/workflow/configuration.rs#L408).

An Opus navigator advising a separately configured coding-model writer is plausible through existing role/message mechanisms. Any active non-coordinator specialist, including a custom role or technical writer, can receive the write claim. However, only one writer owns the repository, and after a candidate exists a new implementation claim requires an allowed rework/continuation condition. Arbitrary alternating writers or adding documentation after a passing candidate is **not** a verified turnkey workflow. A partner who implemented cannot also serve as the final independent reviewer. [Writer eligibility/exclusion](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/repository/claims.rs#L28), [rework gate](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/repository/claims.rs#L117), [review independence](/home/crewroom/Projects/crewroom/server/evidence.ts:132).

**Capacity and obligations need deliberate staging.** Maximum active team is coordinator plus three specialists. Pair + independent reviewer fills it; UX and documentation specialists must participate earlier/later or replace finished specialists. Retirement exists, but a current writer cannot retire. Team choice remains the coordinator's judgment: no inspected admission rule mandates a UI specialist for UI changes, documentation coverage, or both pair members. [Limits/retirement](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-core/src/teams.rs#L184), [selection interface](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/supervisor/workflow/tools.rs#L319).

**New playbooks do not close these gaps by themselves.** They start with an empty catalog, are advisory checklists, and explicitly never grant evidence, ownership or readiness. They are useful scaffolding for a factory policy, but checking a step cannot enforce plan acceptance or establish that an appropriate specialist performed the work. [Playbook contract/default](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-core/src/playbooks.rs#L1).

## Evidence and recommendation

Two integration details affect the next step. Current OMP launch includes `--no-tools` and `--no-skills`; Crewroom supplies its own tools and assembled role prompt. Local Codex/Claude skills are therefore not automatically available merely because they exist on the machine. Reusing their procedures requires explicit import/prompt/tool integration, or new tested runner adapters if the actual Codex and Claude Code runtimes are wanted. The runtime preference was asked during this research and remained unanswered when this assessment was written. [Current launch flags](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/supervisor/workflow/configuration.rs#L408).

The reviewed hosted-provider modules implement Jira and Bitbucket; no GitHub publication adapter was found there. Local task creation and multiple repository configurations are separate capabilities. If the intended projects need GitHub PR publication, include that integration rather than assuming the GitHub location of Crewroom's own source implies it. [Provider modules](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-runtime/src/providers/mod.rs), [local task creation](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/crates/crewroom-core/src/store.rs#L304).

The role-selection test manually supplies fixture roles/models/PIDs and verifies bounded proposals, durable snapshots, restart and rotation; it does not measure whether a live coordinator chooses the right team. Queue tests similarly use fixture models/provider receipts. Historical M5 records a real completed Jira-to-Bitbucket delivery with Opus coordinator/reviewer, GPT implementer and another reporter—not a programming pair. Current status explicitly leaves Linux live-provider delivery unverified and distinguishes scripted native acceptance from historical live evidence. [Assignment test](/home/crewroom/Projects/crewroom/tests/assignments.test.ts:18), [queue test](/home/crewroom/Projects/crewroom/tests/coding-slot.test.ts:23), [live delivery](/home/crewroom/Projects/crewroom/docs/testing/mvp-progress.md:927), [current evidence limits](https://github.com/the-data-sherpa/crewroom-private-archive/blob/dc85a54a24e36b2dc57779bb2b9e46f12fcb26db/docs/status.md#L7).

Recommended next investment: preserve this execution/evidence foundation; add an explicit accepted-plan state and automatic scoping diversion; configure two clear pair roles with one writer and a third independent reviewer; define UI/documentation obligations and staged rotation; then prove two queued jobs plus restart and a UI change using real Linux agents. Use playbooks initially for visibility, with critical gates enforced in workflow state. Choose Paperclip instead only if its broader company/multi-project operations are more valuable than Crewroom's existing revision-bound delivery contract; switching orchestrators alone would not specify the missing pair/plan policy. This is a proposed direction, not an implementation or migration performed by this assessment.
