# LangChain Deep Agents and Crewroom assessment

Tracked by **FOR-20**. Inspected 2026-10-17. The user confirmed LangChain Deep Agents. This assessment inspects source and official documentation; dependencies were not installed, upstream tests and live model calls were not run, and no runtime was changed.

**Recommendation:** study Deep Agents for context management, specialist configuration and model-specific harness behavior while retaining Crewroom's workflow authority. It supplies more ready-made agent behavior than Pi Durable; its persistence, remote delegation and approval mechanisms still need integration with Crewroom's process, delivery and evidence contracts.

## What Deep Agents supplies

The SDK is one part of the product family: **Deep Agents Code (`dcode`)** is a terminal coding agent built on it, while **Managed Deep Agents** supplies the harness and LangSmith Agent Server hosting, including managed storage/runtime configuration. The SDK defaults below do not describe those products' configured persistence. Their live behavior was not audited. [Code overview](https://docs.langchain.com/oss/deepagents/code/overview), [managed architecture](https://docs.langchain.com/langsmith/python/managed-deep-agents-overview#relationship-to-deep-agents).

**It owns the agent harness and delegates execution semantics to LangGraph.** `create_deep_agent` constructs a LangChain agent with filesystem, subagent, summarization and interrupted-tool-history middleware; skills, memory and human approval are configurable additions. Models resolve to LangChain `BaseChatModel` integrations. Supporting OpenAI and Anthropic models therefore does not mean it launches native Codex or Claude Code processes or preserves their sessions. Those integrations would require an additional adapter. [Graph assembly](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/graph.py#L278), [model resolution](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/_models.py#L31).

**Planning is now optional.** Since v0.7, applications explicitly add `TodoListMiddleware` for `write_todos`. These todos are structured agent-state entries, not an application-level acceptance or delivery gate. The framework includes a general-purpose subagent by default, with configurable specialist models, prompts, tools and middleware. [Current overview](https://docs.langchain.com/oss/python/deepagents/overview#task-planning), [subagent configuration](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/graph.py#L431).

**Context isolation, process isolation and sandboxing are different mechanisms.** Ordinary `task` subagents directly invoke a runnable in the host process, with separate messages by default; experimental fork mode inherits conversation context. `AsyncSubAgent` instead uses an Agent Protocol server and exposes launch, check, update, cancel and list operations. Omitting its URL uses co-deployed, in-process ASGI transport; a URL uses HTTP. Separate threads and runs are logical identities, not a guarantee of one observable OS process per specialist. Deployment determines process isolation. [Synchronous dispatch](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/subagents.py#L804), [async specification](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/async_subagents.py#L1).

**Async steering is real, but its semantics need to be preserved.** An update creates a new run on the existing child thread using `multitask_strategy="interrupt"`; the task ID remains stable while the run ID changes. This is stronger than single-result delegation. It is also a cross-system operation: initial launch creates the remote thread and run before returning the parent-state update. From that ordering, an interrupted launch can require reconciliation between remote work and parent records; there is no single atomic commit across those steps. This is a boundary to fault-inject, not a reproduced defect. [Launch implementation](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/async_subagents.py#L686), [update implementation](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/async_subagents.py#L973).

**Persistence is selected, not implied by construction.** SDK defaults are `checkpointer=None`, `store=None`, and `StateBackend()`. State-backed files belong to the conversation; retention across calls and process restarts depends on the configured checkpointer. `StoreBackend` supplies cross-thread files through a supplied LangGraph store, whose concrete implementation determines durability. `FilesystemBackend` stores actual files, while composite routing can combine storage types. These are distinct from the lifecycle and persistence of a remote sandbox. [Constructor defaults](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/graph.py#L278), [state backend](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/backends/state.py#L40), [backend documentation](https://docs.langchain.com/oss/python/deepagents/backends).

**Sandbox adapters govern tool execution environments.** Official integrations include LangSmith, Daytona, E2B, Modal, Runloop and Vercel. They provide filesystem and shell operations in separately provisioned environments. Conversely, `LocalShellBackend` explicitly executes directly on the host without sandboxing. Neither backend choice, by itself, establishes separate supervised model-loop processes. [Sandbox documentation](https://docs.langchain.com/oss/python/deepagents/sandboxes), [local shell contract](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/backends/local_shell.py#L1).

**Context management is the most immediately reusable harness work.** It combines conversation summarization, history/tool-output offloading, progressive `SKILL.md` disclosure and configured `AGENTS.md` memory. Beta harness profiles tune prompts, middleware, tool visibility and default subagents by model/provider. Memory retention follows the selected backend; it is not independently durable. [Context engineering](https://docs.langchain.com/oss/python/deepagents/context-engineering), [skills source](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/skills.py), [memory source](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/memory.py), [profile contract](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/profiles/harness/harness_profiles.py#L1).

**Human approval and unknown effects remain separate concerns.** `interrupt_on` gates selected tool calls through LangGraph interrupts and requires a checkpointer. Interrupted conversation repair inserts an error result when no tool result was recorded; it does not establish whether an external write happened. Applications still need effect-specific reconciliation before treating an interrupted mutation as safely repeatable. [Human-in-the-loop documentation](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop), [history repair](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/patch_tool_calls.py#L11).

## Durability and recovery boundaries

Deep Agents delegates checkpointing to LangGraph. The library's optional checkpointer and store are different from an automatically persistent deployed service. In-memory examples lose their state on process restart; durable storage must be selected for local SDK use. LangGraph's `sync` mode persists checkpoints before advancing, `async` allows persistence alongside the next step, and `exit` saves at run exit. These options describe checkpoint timing, not an atomic transaction with an external tool effect. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [checkpoint modes](https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes).

Resuming a LangGraph interrupt restarts the affected node; effects before the interrupt must be safe to repeat or separated appropriately. Human approval is therefore an execution-control mechanism, not proof that a change satisfies its requirements. [Interrupt semantics](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent).

Cancellation calls the server and then records `cancelled`; that record alone is not Crewroom's verified stopped-ownership receipt for OS processes and tool descendants. A deployment would need to demonstrate that contract. This is a static integration observation, not a reproduced upstream failure. [Cancel](https://github.com/langchain-ai/deepagents/blob/2540af1ecfc61452b2695bcda032db61279ce1bd/libs/deepagents/deepagents/middleware/async_subagents.py#L1079).

## Comparison with Crewroom and Pi Durable

Crewroom baseline: `f79a8d791c22705c21fd7cad2c2338b90f597e28` on `main`. The [Pi Durable assessment](pi-durable-assessment-2026-10-17.md) pins its own inspected source. These are distinct layers with overlapping implementation:

| Area | Deep Agents | Pi Durable | Crewroom |
| --- | --- | --- | --- |
| Primary abstraction | Configured agent behavior through middleware/backends, on LangGraph | Durable conversations, tasks and documents around a model loop | Supervised software delivery across independent harnesses |
| Agent behavior supplied | Subagents, filesystem/context management; configurable skills, memory, profiles and approvals | Extensible tools/tasks; application composes specialist behavior | Accepted plans, named assignments, pairs and staged specialist work |
| Persistence | Configured LangGraph checkpointer/store or deployment service | Single-owner storage with atomic local task/transcript/document commits | SQLite workflow authority plus durable journals, native histories and external receipts |
| Delegation | Inline graph calls or async Agent Protocol threads | Owned child conversations/tasks | Separate OS processes, external Mail, one writer and explicit handoffs |
| Completion policy | Application adds domain-specific gates | Application adds domain-specific gates | Exact candidate/check/review bindings and reconciled Jira/PR delivery |

Crewroom's [product](../product.md) and [architecture](../architecture.md) require independent observable processes, native OMP/Codex/Claude adapters, external messages, bounded replacement and human merge. Source anchors are the [runner interface](../../crates/crewroom-runtime/src/runner/mod.rs), [native session journal](../../crates/crewroom-runtime/src/runner/journal.rs), [stopped ownership](../../crates/crewroom-runtime/src/supervisor/hosts/recovery.rs), [external messages](../../crates/crewroom-runtime/src/messaging.rs), [package rules](../../crates/crewroom-core/src/choreography/mod.rs) and [readiness gate](../../crates/crewroom-runtime/src/evidence/readiness.rs). Neither an isolated context window nor a successful graph result satisfies those contracts by itself.

## Recommendation

Deep Agents is a more complete starting point for **agent behavior** than Pi Durable: more delegation, context and environment choices are already assembled. Pi Durable is particularly relevant to the **durable task abstraction**. This is an architectural assessment, not a performance or reliability ranking.

For a new Python application that owns its model/tool loop, Deep Agents could avoid considerable harness implementation. For existing Crewroom, adopting it wholesale would still leave the product workflow, process supervision, native-harness integration, message receipts and evidence gates to maintain. Preserve those boundaries.

The most useful ideas to evaluate are:

- **Retrievable context instead of repeated large inputs.** Crewroom already has [bounded continuation projections](../../crates/crewroom-runtime/src/supervisor/workflow/context.rs) and retained artifacts. Compare Deep Agents' progressive skills and offloading with that implementation; improve selective retrieval while preserving source/revision identity and full evidence outside the prompt.
- **Explicit model-specific harness profiles.** Tool descriptions and context behavior can be tuned per model. Crewroom already freezes model routes and instruction snapshots; any comparable tuning should be versioned and evaluated through the existing [instruction comparison contract](../testing/for-14-comparison-contract.md).
- **Reusable specialist configurations and remote task lifecycle.** Study their interface, but map it to existing Crewroom roles/assignments. Do not create a second assignment authority or silently move specialist work into internal subagents.

If evaluating the actual dependency, begin with one read-only research specialist in its own supervised process. Disable internal delegation and direct mutation paths; use Crewroom-authorized tools and external Mail. Select durable checkpoints explicitly, then test restart, duplicate input, lost launch responses, steering, cancel/descendant cleanup and result provenance. Compare context usage and useful output against the existing runner with identical input; this task supplies no such benchmark. A successful spike could justify an additional runner, not replacement of the workflow service. No integration is adopted here.
