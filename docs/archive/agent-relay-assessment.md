# Agent Relay and Relaycast assessment

Research date: 2026-09-25. Source inspection only; no dependency installation, downloaded-code execution, services, accounts, or message sending.

Pinned sources: Agent Relay [`635cfacd78000b2c023d51bd587ed1ea6a5601db`](https://github.com/AgentWorkforce/relay/commit/635cfacd78000b2c023d51bd587ed1ea6a5601db), and Relaycast [`130c8204886acdb111ee2fd67774dacf5b4e4637`](https://github.com/AgentWorkforce/relaycast/commit/130c8204886acdb111ee2fd67774dacf5b4e4637).

## Recommendation

**Shortlist the messaging SDK plus self-hosted Relaycast for a bounded comparison with a small Crewroom-owned mailbox.** This is a closer fit to Crewroom's local communication needs than adding an email infrastructure dependency: identities, conversations, files, durable message delivery, and optional runtime adapters are distinct capabilities. This is an assessment, not adoption or a claim of tested OMP compatibility.

Crewroom must retain assignment authority, execution authorization, applied-steering observations, code-revision evidence, and external-action reconciliation. Relay can provide a communication substrate; the documented SDK idempotency claim requires qualification for the default self-hosted runtime.

## Useful implemented boundaries

The SDK separates messaging, delivery, actions, and optional managed execution. An application that already owns its runner can use `@agent-relay/sdk`; `@agent-relay/harness-driver` manages processes separately. The SDK supports named registered agents, reconnecting with a persisted agent token, channels, DMs, group DMs, threads, and events. [SDK contract](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/sdk/README.md#L1-L98)

Relaycast's Node adapter opens SQLite, supplies API-key authentication and local file storage, and starts delivery maintenance. Its self-hosting guide describes one process without external database/broker requirements. Workspace keys administer a workspace; agents get separate tokens. Agent Relay SDK requires Node 22+, while the server guide lists Node 20+ and a native `better-sqlite3` build prerequisite. [Node assembly](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/adapters/node/index.ts#L90-L192), [prerequisites](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/docs/self-hosting.md#L1-L26), [credentials](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/docs/self-hosting.md#L128-L151), [SDK package](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/sdk/package.json#L1-L6)

Channel message creation groups message, attachment relationships, session reference, delivery records, and log writes through the atomic-write abstraction. This is substantive reusable machinery. Arbitrary metadata can carry Crewroom IDs, but neither a file attachment nor a session reference proves a test/review covers the current revision. [Message implementation](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/engine/message.ts#L21-L129)

## Delivery is not application

SDK sessions return `accepted`, `delivered`, `deferred`, or `failed`. Relaycast's durable delivery states separately mean queued, sent to a location, acknowledged by that location, or failed/dead-lettered. These are useful distinctions, but none establishes that an agent incorporated steering into its plan or completed an assignment. [Session receipts](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/sdk/src/session/types.ts#L124-L169), [server states](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/types/src/delivery.ts#L3-L57)

`DeliveryRunner` drains an inbox into `receiveMessage` or legacy `inject`, then acknowledges, defers, or fails the item. Its session delivery mode defaults to **immediate**. `stop()` sets a local flag; it is not a confirmed interrupt of work already handed to the agent. Crewroom must explicitly prevent dispatch while paused and implement safe interruption/reconciliation. [Runner control](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/sdk/src/delivery/runner.ts#L27-L98), [dispatch/default mode](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/sdk/src/delivery/runner.ts#L100-L161)

The inspected public harness factories and native adapter registry contain Claude, Codex, OpenCode, Pi, and others, **no OMP/Aperture entry**. Native entries are marked experimental. Pi support does not establish compatibility with this machine's OMP executable. A custom session/harness is supported, so the promising path is an OMP RPC adapter behind that interface, with separate contract tests. [Public factories](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/harnesses/src/index.ts#L8-L42), [native registry](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/packages/harnesses/src/ai-sdk/adapter-registry.ts#L113-L194)

## Restart and duplicate handling

**Durable delivery records do not imply durable send deduplication.** The default Node runtime constructs an `InProcessKeyValueStore`; that implementation is a memory Map. Generic idempotency stores successful responses there after the operation, with a best-effort read/write lock explicitly documented as non-atomic. [Runtime wiring](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/adapters/node/index.ts#L131-L170), [KV implementation](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/adapters/node/kv.ts#L11-L55), [lock semantics](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/middleware/idempotency.ts#L185-L213), [response storage](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/middleware/idempotency.ts#L246-L270)

For ordinary channel sends, the route passes the key only to that middleware; the message engine generates a new ID. After a server restart loses the KV record, retrying an accepted send can therefore create another message. This is a code-derived failure scenario, not a reproduced runtime result. [Channel route](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/routes/message.ts#L141-L165), [fresh ID](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/engine/message.ts#L21-L37)

Ordinary local DMs have the same generic middleware. DM code also contains stronger database-backed A2A ingress/egress bindings; those special paths must not be generalized to all DMs. A local non-A2A recipient gets a fresh generated message ID without those bindings. Consequently, any adoption test must cover **ordinary coordinator/specialist messages**, not just an A2A or workspace-create replay test. [DM route](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/routes/dm.ts#L104-L122), [A2A replay and conditional admission](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/engine/dm.ts#L494-L591)

There is an important source/documentation inconsistency: self-host limitations say webhook delivery cannot survive restart. **The inspected Node implementation does persist webhook work**: it constructs and starts `DurableEventQueue`, whose `send()` awaits outbox insertion and whose startup polls retained rows. The source supersedes that stale limitation for this revision; it does not eliminate every gap between message admission, external delivery, and application acknowledgement. [Stale guide](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/docs/self-hosting.md#L311-L330), [actual wiring](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/adapters/node/index.ts#L138-L144), [outbox implementation](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/packages/engine/src/adapters/node/event-queue.ts#L46-L107)

## Release scope and next experiment

Both repositories are Apache-2.0. Relaycast's inspected commit is identical to release **v8.13.0**, published September 25; Relay's inspected main is seven commits beyond **v12.4.1**, published September 22. Thus these are not uniformly release-tag observations, and package compatibility remains to be exercised. [Relay license](https://github.com/AgentWorkforce/relay/blob/635cfacd78000b2c023d51bd587ed1ea6a5601db/LICENSE), [Relaycast license](https://github.com/AgentWorkforce/relaycast/blob/130c8204886acdb111ee2fd67774dacf5b4e4637/LICENSE), [Relay comparison](https://github.com/AgentWorkforce/relay/compare/v12.4.1...635cfacd78000b2c023d51bd587ed1ea6a5601db), [Relaycast release](https://github.com/AgentWorkforce/relaycast/releases/tag/v8.13.0)

Before adopting it, test two separate OMP sessions with a local Relaycast instance: message while paused, duplicate sends, lost send response plus restart, crash after OMP receives input but before relay acknowledgement, reconnect with pending work, and applied-steering reporting. Require durable logical-message deduplication, explicit uncertainty when delivery cannot be established, and recovery without extra execution. Keep coordinator-visible transcripts and evidence in Crewroom regardless of the transport selected.
