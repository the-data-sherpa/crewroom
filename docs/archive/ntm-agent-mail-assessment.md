# NTM and Agent Mail for Crewroom communication

Researched 2026-09-25 America/New_York (the Rust main commit inspected is dated 2026-09-26 UTC). This is source and documentation research, not a runtime evaluation. Public repositories were checked out under `/tmp`; no downloaded code, installers, tests, services, model sessions, or external mutations were run. This supplements, rather than replaces, [the earlier NTM assessment](ntm-fit-assessment.md) and [workflow-gate research](ntm-workflow-gates.md).

## Recommendation

**Treat durable mail, agent wakeup, and workflow authority as separate components.** Agent Mail is the relevant candidate for reusable inboxes and threaded exchanges. NTM is a much larger terminal orchestration system whose OMP integration sends terminal input and interprets the TUI. Crewroom's partially tested OMP RPC transport can be paired with a mailbox without adopting NTM. Neither mailbox receipts nor terminal activity establish that an instruction was applied or a coding assignment passed its quality gates. [NTM delivery implementation](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/dispatch/dispatch.go#L373), [Python message records](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/models.py#L76), [Rust receipt implementation](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L4650).

Within this family, **Rust Agent Mail merits the first bounded mailbox contract experiment** because its inspected source has retry keys, durable recipient event cursors, and message-bound delivery receipts. Python is easier to reason about at the API boundary but lacks those send/replay contracts in the inspected signature. Rust is not a drop-in semantic replacement: reads, reservations, identity policy, and archive acknowledgement differ. Resolve the license condition below before adoption; no dependency is selected by this report.

## Mail and wakeup are different operations

Agent Mail provides project-scoped identities, sender/recipient routing, message IDs, threads, replies, inboxes, explicit acknowledgements, and searchable archives. It stores mail in a database and creates Git-readable artifacts. It does not itself make an idle OMP model consume the mailbox. Python's optional notifications create debounced, best-effort signal files; fetching the inbox clears a signal. A signal is a wakeup hint, not a durable queue item or evidence that an agent read the message. [Python notification code](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/storage.py#L3618), [message/recipient schema](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/models.py#L76).

NTM's optional `mail_nudge` bridges that gap. Its coordinator polls registered agents' inboxes, checks fresh pane state, and types a prompt asking an idle agent to check its mail. It is off by default, applies a default 60-second cooldown, records nudge attempts, and publishes delivery/skip outcomes. This is separate from storing the assignment in Agent Mail. Current main's shared safety check recognizes OMP. [Nudge implementation](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/coordinator/mail_nudge.go#L1), [OMP safety check](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/coordinator/rotation.go#L442).

For OMP, NTM uses tmux prompt submission, Escape interruption, screen-derived activity/context, and native session reopening. This is **terminal automation, not OMP JSON RPC**. Its documented fixtures are based on OMP 18.2.3, while Crewroom's prior probe used installed 18.3.1. Those paths need separate compatibility tests. [Pinned OMP documentation](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/README.md#L301), [actual SendKeys dispatch](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/dispatch/dispatch.go#L373).

## Receipt semantics and a concrete compatibility risk

| Operation | Python main | Rust main |
|---|---|---|
| Fetch inbox | Does not change read/ack state; default returns up to 20 recent messages | Defaults to marking returned messages read, even when bodies are omitted; `mark_read=false` requests a peek |
| Mark read | Sets this recipient's read timestamp | Same concept |
| Acknowledge | Sets read and acknowledgement timestamps; repeated acknowledgement preserves prior timestamps | Same concept, plus optional retry key |
| Delivery receipt | Send result contains stored message details | Additional receipt distinguishes persisted, signaled, acknowledged |
| Applied or completed | No application-level execution proof | No application-level execution proof |

[Python fetch](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L9592), [Python acknowledgement](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L9921), [Rust read behavior](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L4337), [Rust receipt](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L4650).

**Source-derived integration risk, not a reproduced bug:** NTM's current `FetchInbox` client does not send `mark_read=false`. Its mail nudge then counts entries with no read timestamp. Rust's default fetch sets those timestamps and returns the updated rows. Consequently a monitor can mark mail read before the specialist consumes it and suppress the intended nudge. Python does not have this default. An adapter must negotiate/pin semantics and monitoring must not consume recipient state. [NTM request construction](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/agentmail/tools.go#L249), [nudge read counting](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/coordinator/mail_nudge.go#L344), [NTM accepts both timestamp spellings](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/agentmail/types.go#L140), [Rust timestamp propagation](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L4724).

## Ordering, retry, and recovery

Python inbox polling is newest-first, bounded by a limit, with a strictly-newer-than timestamp filter. Its send signature has no caller idempotency key. Therefore a timestamp plus a capped recent-inbox query is insufficient as a general lossless queue cursor: a busy interval can exceed the page size, and equal timestamps need care. A lost send reply cannot safely be treated as permission to repeat the send. This is an inference from the API and query, not a claim that Python mail is never durable. [Python inbox query](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L4463), [send signature](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L7132).

Rust improves that contract in two ways:

- Keyed send/reply calls replay the original message ID for the same arguments and reject a changed payload under the same key. The documented default retention is 24 hours, scoped to project and tool. This is bounded deduplication, not indefinite exactly-once agent execution. The database stores the request result with message creation. [Send implementation](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L2840), [transaction implementation](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-db/src/queries.rs#L8001).
- `fetch_inbox_events` is an oldest-first recipient feed with an independent cursor, page continuation, and explicit expired/ahead errors. It is body-free and does not mark messages read. A consumer persists its cursor after processing, then uses the message ID to obtain content. This supports restart-safe ingestion; it does not atomically couple agent execution to cursor advancement. [Cursor implementation](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L4503).

The database/archive boundaries also differ. Python commits message rows, attempts the archive bundle, and compensates by removing rows if the archive write fails. Rust regards the database as authoritative and schedules archive materialization; source explicitly allows archive lag, ephemeral fallback, or dropped archive work under failure conditions. A successful Rust send is not proof the Git archive is already complete. Preserve and back up operational state; do not assume a Git-only restore preserves all message, receipt, and cursor state. [Python compensation](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L5670), [Rust archive dispatch](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L45).

NTM has its own durable assignment ledger. It distinguishes guaranteed pre-dispatch rejection from timeout/transport uncertainty: the latter retains an outcome-unknown barrier instead of blindly sending again. Pending recovery reuses recorded assignment intent and validates target identity. This is valuable workflow machinery, but it is a separate layer from mailbox delivery and from Crewroom's evidence gates. [Dispatch uncertainty](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/coordinator/assign.go#L1360), [pending recovery](https://github.com/Dicklesworthstone/ntm/blob/b470fc2fb187b01eab1b43ae8bbdfdebe2611e6f/internal/coordinator/assign.go#L640).

## Reservations are not filesystem isolation

Python reservations report overlap but still grant conflicting leases. Rust main grants only non-conflicting paths and repeats the conflict check inside the database transaction. Both are coordination records: neither prevents a process with ordinary filesystem access from editing a file. Optional Git hooks can block conflicting commits/pushes, but that is not an operating-system write boundary. Crewroom must retain owned worktrees and its one-writer rule. [Python grant behavior](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L11614), [Rust grant behavior](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/reservations.rs#L1915), [Rust guard boundary](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/README.md#L875).

## Operator visibility, identity, and operational cost

Python supplies browser inbox, thread, search, reservation, archive, and overseer-message routes. Rust adds extensive CLI/robot, TUI, and browser surfaces. These are useful visibility references; a second full operator console would duplicate parts of Crewroom. Rust also includes an autonomous ATC operator, on by default with effects in shadow mode; a mailbox experiment should disable it so Crewroom remains the sole workflow authority. [Python routes](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/http.py#L2710), [Rust operator surfaces](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/README.md#L764), [ATC configuration](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/README.md#L1141).

Do not use an agent's friendly mail name as proof of runtime identity. Crewroom needs an explicit mapping from role/run/assignment/attempt to mailbox identity and OMP session ID, including replacement generations. Identity behavior also needs an adapter contract: Python fetch/ack authenticate a session or registration token; Rust's send schema permits an omitted sender token and reports `verified_sender=false`, subject to configured proof policies. [Python authentication call](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/src/mcp_agent_mail/app.py#L9668), [Rust send identity contract](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-tools/src/messaging.rs#L2137).

The dependency choices are substantial. Python declares Python 3.12+, FastMCP/FastAPI, SQLAlchemy/SQLModel, SQLite, GitPython, and several supporting packages; its package metadata labels it alpha. Rust main pins a nightly compiler and a larger stack including FastMCP Rust, Asupersync, FrankenSQLite/SQLModel, and search dependencies. NTM adds tmux and a Go binary plus whichever companion integrations are enabled. The repositories contain targeted concurrency, idempotency, conformance, and recovery tests; their existence is encouraging, but none were run for this report. [Python metadata](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/pyproject.toml#L5), [Rust compiler](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/rust-toolchain.toml), [Rust dependencies](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/Cargo.toml#L29), [Rust idempotency tests](https://github.com/Dicklesworthstone/mcp_agent_mail_rust/blob/ca7bc98d461aefe1c52b304ec71aab003039ed80/crates/mcp-agent-mail-db/tests/idempotency_integration.rs), [Python concurrency tests](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/4b11f26277f611e60bcfdb3858c305d1af2fcc53/tests/test_concurrent_writes.py).

## License is an adoption condition

All three inspected `LICENSE` files carry an OpenAI/Anthropic rider. They define restricted parties to include the named companies, affiliates, and parties acting on their behalf/for their benefit/under their direction, then state: **“no rights are granted to any Restricted Party.”** The terms also restrict making the software available to those parties and define covered use broadly. These files should not be described as ordinary MIT despite Python package metadata saying MIT. Rust metadata explicitly uses `LicenseRef-MIT-Rider`. This report does not determine the user's legal eligibility; confirm the intended use's permission before integrating or redistributing code. ## Proposed Crewroom boundary and acceptance experiments

Keep a small provider-independent message contract in Crewroom: immutable message ID; run, assignment, and attempt IDs; sender/recipient identities; message kind; correlation/parent ID; revision or artifact references; delivery state; and explicit application acknowledgement. The workflow service owns the durable outbox, dispatch authorization, pause/cancel behavior, session generations, and evidence gates. A mailbox may supply storage/threading/search. The OMP adapter owns live wakeup and session control. This is a design recommendation, not implemented behavior.

Use coordinator-to-specialist assignment and specialist-to-coordinator results first. Allow addressed specialist questions/findings later through the same recorded service, with coordinator visibility and bounded recipients. A specialist message must not by itself change scope, grant write ownership, or advance a quality gate.

Before adopting either implementation, prove the following against pinned builds:

1. Store mail for a stopped/paused specialist; show it as pending; neither monitor nor mailbox autonomously starts execution. Resume deliberately through OMP RPC.
2. Crash after send persistence but before reply; retry with the same ID/key; recover one logical message. Repeat after dedup retention and require explicit reconciliation rather than assume unlimited deduplication.
3. Deliver more than one inbox page while the consumer is offline; include identical timestamps and concurrent senders. Recover every addressed message with durable cursor progress and bounded replay.
4. Crash before and after agent acceptance, and before and after application acknowledgement. Show persisted, wakeup-requested, runner-accepted, agent-applied, and completed as distinct facts.
5. Confirm operator/header-only monitoring does not mark the specialist's mail read; exercise the Python/Rust difference and the NTM nudge incompatibility above.
6. Replace a specialist session; fence the old generation; prevent old replies from advancing the replacement assignment. Reject forged sender/run/assignment combinations.
7. Fail the archive writer and restart the service. Verify which mail/receipts/cursors survive and show archive lag truthfully; separately test database restoration.
8. Request conflicting leases concurrently and expire them while a process is alive. Verify the actual grant policy and retain Crewroom's exclusive writer admission regardless of advisory state.
9. Send a peer clarification while the coordinator is paused or the execution budget is exhausted. Record it without bypassing workflow controls or starting an agent conversation loop.

These are contract tests for the communication boundary. They do not replace the approved the pilot repository pilot's revision-bound checks, independent review, Jira updates, or human merge gate.
