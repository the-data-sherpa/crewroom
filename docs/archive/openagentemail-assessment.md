# OpenAgentEmail assessment

Research date: 2026-09-25. Candidate: [openagentemail/openagentemail](https://github.com/openagentemail/openagentemail). Read-only source inspection at commit [`5ce4ae2b055a0ba5bf092da283190e79efd78938`](https://github.com/openagentemail/openagentemail/commit/5ce4ae2b055a0ba5bf092da283190e79efd78938), committed 2026-09-25. No packages installed, downloaded code executed, services deployed, credentials used, or messages sent. This is source and first-party evidence, not a Crewroom integration test.

## Recommendation

**Keep OAE as an optional future mailbox adapter; do not make it Crewroom's local execution or recovery authority.** It implements real task communication beyond ordinary email: named identities, participant authorization, task history, structured results, approvals, leases, and recoverable webhook delivery. Its storage and delivery model adds SMTP/IMAP and a second task lifecycle to a local application that still needs its own durable assignments, process controls, evidence gates, and reconciliation. That is an architectural inference from the boundaries below, not a claim that the project is unusable.

OAE becomes more attractive if Crewroom must exchange work with independently operated agents across terminals or machines, especially where human-readable mail matters. Those agents can use one OAE instance remotely. **Independent OAE-instance task federation is still proposed**, despite ordinary email being federated. The federation RFC explicitly says there is no implementation. [Federation RFC](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/docs/rfcs/0002-federated-signed-tasks.md#L1-L28)

## Delivery and recovery are the deciding boundaries

**Task creation is not idempotent after a lost response.** The create schema has no caller-provided idempotency key, and production generates a new UUID on each call. The documented response-loss procedure is to inspect task history before creating again. Idempotency fields elsewhere in the implementation do not change this create contract. [Create schema](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/api/src/routes/tasks.ts#L31-L50), [UUID generation](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/api/src/lib/tasks-internal.ts#L2143-L2161), [documented uncertainty](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/docs/first-task-handoff.md#L79-L87)

Webhook delivery records pending metadata before scheduling. This supports recovery of already-recorded delivery work. However, the mail watcher starts at the current high-water mark and returns no existing UIDs on first sight. Mail received while the API was down therefore requires consumer reconciliation; restart of the webhook queue alone is insufficient. [Pending write](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/api/src/lib/webhook-delivery.ts#L2625-L2660), [watcher initialization](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/api/src/lib/notification-watcher.ts#L216-L238)

Notifications are not applied steering. The stronger checked-in wake adapter targets **Orca**, sends a fixed neutral notice to a statically bound terminal, and calls success transport submission. It uses at-least-once semantics; a crash between sending and committing deduplication can duplicate a wake. It does not implement OMP RPC, useful-turn interruption, session continuation, or Crewroom's pause gate. [Wake contract](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/examples/webhook-wake/README.md#L3-L59)

Optional task leases provide claim/renew/release and generation fencing. Both leases and their pending journal default off. Journal startup requires deliberate provisioning, stable signing keys, and a single writer; the operating guide describes no supported signing-key rotation/reseal procedure. These fences cannot stop an already running specialist from modifying a file. [Flag definitions](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/api/src/lib/config.ts#L153-L167), [journal contract](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/docs/task-lease-journal.md#L1-L35), [external-effect boundary](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/docs/architecture.md#L99-L108)

Relevant upstream issues were open on the research date. These are maintainer-reported limits, not newly reproduced defects:

- [#262](https://github.com/openagentemail/openagentemail/issues/262): the same underlying mail can generate a new event ID and bypass wake deduplication based only on event ID.
- [#184](https://github.com/openagentemail/openagentemail/issues/184): a post-accept journal publication failure can leave a successful lease response followed by a corrupt journal on reload.
- [#182](https://github.com/openagentemail/openagentemail/issues/182): unresolved lease records can remain open after task termination and consume bounded journal capacity.
- [#362](https://github.com/openagentemail/openagentemail/issues/362): MCP message reads lack REST's mailbox-generation parameter; a mailbox rebuild can make an old UID identify different mail.
- [#364](https://github.com/openagentemail/openagentemail/issues/364): newer headless responder examples retain timeout, acknowledgement, and generation-check limitations. These templates are not a ready-made durable Crewroom worker adapter.

## Operations and maturity

OAE uses Bun/Hono with IMAP/SMTP libraries. Its stdio MCP package requires Node 20+. Deployment is either a bundled docker-mailserver/ntfy stack or an API container connected to an external catch-all mailbox; the API-only contract still requires domain, IMAP/SMTP credentials, signing secret, and persistent state. It defaults the API host binding to loopback. This is a real additional service dependency for Crewroom. [API package](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/api/package.json), [MCP package](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/packages/mcp/package.json), [API-only deployment](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/compose.api-only.yaml#L1-L58), [loopback binding](https://github.com/openagentemail/openagentemail/blob/5ce4ae2b055a0ba5bf092da283190e79efd78938/compose.api-only.yaml#L118-L123)

## If we evaluate an adapter later

Crewroom should retain its authoritative message/outbox record, run/assignment/attempt IDs, dispatch authorization, receipt/application observations, ownership, and evidence. An OAE task or message ID would be an external reference. OAE notifications would accelerate reconciliation, never independently start paused work. This is a recommended integration design, not implemented behavior.

The minimum discriminating experiment is two distinct OMP sessions exchanging one structured request and result through OAE while Crewroom handles: a lost create response, duplicate notification, API downtime, mailbox-generation change, controller restart, and a message arriving while paused. Verify eventual reconciliation without duplicate execution, separate saved/received/applied states, exact revision evidence, and coordinator visibility of a specialist-to-specialist exchange. Measure added latency and operational burden against a local durable mailbox plus the already-probed OMP RPC transport. Do not enable lease journals or adopt example responders as a shortcut around those tests.
