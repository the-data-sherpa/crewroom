# Native migration execution ledger

Historical ledger: required N1–N7 work is accepted within the [native release record](release-native.md). The branch and iteration instructions below describe that completed migration. Current development follows [status](status.md#continuation-order) on `main` and Linear CrewRoom; optional compatibility follow-ups remain explicitly unverified.

The operator requested on 2026-10-02 that the remaining migration be planned and executed iteratively, with a commit and push at the end of every iteration. This ledger expands [N1–N7](native-migration.md#ordered-migration-and-acceptance); it does not reduce the accepted product scope. Continue on `codex/rust-gpui`, pushing to `origin/codex/rust-gpui` after each passing iteration. Keep unrelated operator files out of these commits. At the end of each iteration, report completed work, validation, the committed and verified remote revision, remaining work and the next step. Evaluate whether the iteration advanced the full migration, and identify scope drift or avoidable overhead. This reporting requirement was added by the operator on 2026-10-03.

## Iteration protocol

1. Inspect the current status, this ledger and the relevant TypeScript contracts and fixtures. Name the iteration and its observable acceptance conditions before editing.
2. Port the complete transaction or boundary, including refusal, replay, interruption and reopen behavior. Preserve existing runtime data and keep unvalidated capabilities unavailable.
3. Run focused native/oracle checks and Rust workspace tests/build/format/Clippy. Run `npm test` for domain/service changes, `npm run build` for retained TypeScript type/build changes, and `npm run test:e2e` for user-flow changes. For desktop-only iterations, source-bound retained domain/build results may be reused only after verifying every retained input is byte-identical; record the original revision and receipt. Fresh native interactions remain required and retained browser results never substitute for them. Run all suites afresh for final cutover. Use source-bound receipts; distinguish real processes and Git from scripted provider replies. Preserve earlier failures. A documented unchanged rerun of a known intermittent does not become a claim that the original invocation passed.
4. Update `docs/status.md`, `docs/testing/mvp-progress.md`, this ledger and machine-readable evidence. Commit the iteration, push without force, and verify the remote branch points to that commit before starting the next iteration. If publication is rejected, retain the local commit and report the specific blocker; never silently treat a failed push as success.

## N2.4 acceptance detail

N2.4 is split into three commit/push boundaries because durable delivery, team changes and cross-store role approval have different interruption cases. N2.4a checks the 100-message backlog, keyed replay at capacity, exact delivery histories, stopped-input restoration and atomic writes across related records. Its clock-controlled oracle covers records only; external Mail and host evidence remain N3.3.

N2.4b must preserve queued insertion reservations during launch edits and admission; reject disabled roles or changed accepted scope before a stop; keep the original proposal/model snapshot; use a newer role instruction revision only when model and effort still match; and retire/admit the whole team atomically after confirmed stops and reconciled input. Operator proposals must hold readiness until their admitted responsibility is closed. No native insertion endpoint may bypass the unported model-validation boundary.

N2.4c must validate proposal evidence against its run, save approval before changing the role catalog, reconcile a failed catalog save without a second version increment, reject a competing role/project-guidance revision, and leave existing assignment snapshots immutable. Test both sides of the catalog-write/SQLite-completion crash window with isolated user configuration. The retained pilot and real role catalog are not fixtures.

The N2.4c role-file pass must also align stored-role parsing and request/provenance UUID validation with the installed schema. The current Rust UUID parser accepts textual forms beyond the TypeScript UUID validator; reject those at request boundaries while retaining valid historical records. Include Unicode trimming, unknown-field stripping, required catalog size, optimistic revision and non-forgeable learning provenance in its compatibility cases.
