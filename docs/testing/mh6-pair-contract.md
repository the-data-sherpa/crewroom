# MH6 pair and package contract

FOR-11. Implementation began 2026-10-13 against `d399031679269f765c37e7b0e648767624855360`. Acceptance evidence belongs in the [progress record](mvp-progress.md); this contract does not certify a live run.

## Authority and identity

The accepted MH5 plan stays immutable. A run captures execution policy version 1 at its first coding admission. A separate, revisioned choreography binds its plan ID, content hash, requirements revision and named packages to a staged schedule. Proposed assignments reserve no process. The existing coordinator proposes; the service admits current roles and verified model routes, then freezes the brief, package scope and responsibility on each assignment. The existing queue owns the single coding slot.

A stage has at most three specialists, in addition to the coordinator. Assignment dependencies refer to admitted assignment identities; package dependencies refer to the accepted plan. A future stage cannot satisfy either kind of execution evidence. The writer and read-only navigator are separate assignments. UI jobs declare UI expertise; diagnosis is selected for a stated problem. Every package has documentation ownership, even when its outcome is a reasoned no-change decision. A separate final reviewer excludes the pair and every contributor, across retired assignments and replacement sessions.

## Package lifecycle

| State | Permitted next state | Required fact |
| --- | --- | --- |
| Proposed | Active | Current binding, admitted owner and completed package dependencies |
| Active | Blocked | Concrete unresolved concern retained |
| Blocked | Active | Reasoned resolution retained |
| Active | Complete | Outputs, documentation disposition and delivered navigator exchange resolved |
| Complete | Active | Explicit rework under existing review/check/Resume authority; retain previous closure |

No lifecycle label grants write access. Claiming a writer also requires the current assignment's writing responsibility, active package scope, one writer lease, current requirements and existing process/Git checks. Manual launch, saved launch, scheduled admission and insertion use the same policy. Standalone Explore, Grill and research retain their existing behavior.

## Exchange and reports

A structured exchange retains package, source checkpoint, artifact, concern, proposed test/change and a response/disposition. Writer approach, navigator challenge and writer response use the existing addressed external Mail ledger. Persist the logical message before delivery; its existing external and host receipts distinguish pending, stored, accepted and received. A lost reply reuses the same logical identity. Superseded attempts cannot close current obligations. Closure requires a concrete challenge and evidence-backed resolution, not a message count or praise. Reports are bounded, keyed and append-only; a changed retry conflicts.

The exchange tool returns its durable pending intent. The existing delivery loop sends it and reconciles external and runner receipts independently, so a daemon restart during transport does not strand a provider tool reply. Report retries resolve the saved request before reading mutable files. A later verified contribution to the same path supersedes its current artifact obligation; earlier report snapshots and source identities remain immutable.

## Checkpoint, handoff and freeze

`checkpoint_implementation` records the current writer, intended successor and observed head/content before requesting the existing whole-run stop. Stop and reconcile agents, tools and messages; checkpoint Git once through the existing completion marker; release the old lease before any new claim. A successor is intent until admitted and granted the lease. Unknown ownership, changed content/requirements, busy descendants, pending effects or newer Pause/Cancel intent holds progress. A checkpoint creates no candidate and spends no automatic repair cycle.

`finish_implementation` freezes only after every package output, required specialist report, documentation decision and navigator concern is closed. All contributors' attempts are retained. All agents and writing must be stopped, and the exact clean revision must match the request. One keyed freeze yields one candidate containing both code and documentation. Candidate checks and final independent review retain the existing revision/artifact gates. Later changes reopen affected work and require fresh evidence. An unchanged outcome creates no artificial commit.

PR/check observations may revoke readiness; only explicit operator Resume admits PR-feedback work. Existing recovery counters, target-refresh policy and human merge remain authoritative. No exchange or package closure substitutes for required checks or independent final review.

Native Pause and Cancel remain available during a slow Resume. Stops bypass the ordinary read/command queue and supersede queued starts. Native Resume carries the observed control revision; admission checks it under the service's store lock. Every explicit Pause advances that revision even when already paused, so an older Resume arriving later cannot undo it. Already-admitted continuations retain the existing desired-state/revision checks throughout process startup.

Explicit requirements adoption prevents restoration of a stale writer. Retire the superseded specialists through the existing stop/reconcile path, accept a current immutable plan version, then propose a successor schedule covering every old and current package with fresh assignment names. The new binding starts fresh package generations while preserving prior reports, exchanges and revisions. Acceptance of a plan alone never grants a writer lease.

## Compatibility and failure policy

Schema 29 is additive. Already-admitted legacy runs retain their captured behavior and history; no pair evidence is invented. Unadmitted jobs adopt policy 1 before coding admission, including explicit successor runs. Matching-binary whole-state restoration includes roles, plan/choreography, ownership, Mail receipts, repository paths and evidence. Older binaries are not promised compatibility.

Every transition compares the current choreography and requirements revision inside the transaction. Replay returns the saved result before applying a new transition; altered content conflicts. A transaction failure changes neither revision nor receipt. Stage rotation and handoff use existing stop/reconcile transitions and admit no replacement until old ownership is established. Readiness, direct candidate registration and publication all consult the same choreography obligations.

## Validation gates

Executable core cases cover lifecycle, full package coverage, cycles, responsibility/permission rules, capacity, immutable binding, stale revisions, duplicate requests, restart and transactional rollback. Runtime cases cover actual Git checkpoints, stale-writer denial, explicit ownership transfer, freeze/review bypass attempts and external Mail recovery. Native journeys distinguish future assignments from observed processes and retain challenge/report/blocker history at wide and 390px widths. Two live disposable jobs (backend and UI) must demonstrate different teams, meaningful challenge, documentation handoff, independent review and interrupted recovery across the supported harness matrix. Simulated provider checks remain labelled separately.
