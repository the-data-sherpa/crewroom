## Failures and required changes

### 1. Message deduplication does not survive mailbox restart

Send a message using an idempotency key, terminate Relaycast, restart against the same database, and repeat the send with the same key. The service creates a second message with a different ID. Deduplication works while the original service process remains alive; pending deliveries also survive restart. Those are separate properties.

This fails the desired lost-acknowledgement contract when relying on the mailbox key alone. Crewroom needs a durable outbound action record and reconciliation before retrying an uncertain send. Receivers also need durable logical-message deduplication. Do not assume exactly-once delivery or blindly retry publication/Jira operations by analogy with the happy-path mailbox test.

Related cases: MSG-03, MSG-05, MSG-07; uncertainty policy also informs DEL-03. This is a dependency/adapter gap, not a demonstrated bug in an implemented Crewroom service.

### 2. First-turn RPC visibility does not establish persistence

Start a fresh OMP session, submit an input, hold its first provider response, confirm the input appears through `get_messages`, then kill OMP. In the tested configuration, the input was absent from the session file before termination. Reopening that path returned a new session ID and did not recover the input.

A separate test first completed a checkpoint, then verified the new incoming message in the actual session file before killing the specialist. That recovery passed, preserving the session and exactly one copy of the incoming message. The four-hop exchange also completed after a later coordinator-process restart; all mailbox receipts matched and no pending deliveries remained.

Crewroom must retain incoming messages independently and distinguish RPC observation, durable storage and completed work. Its delivery/recovery policy cannot acknowledge a message solely because OMP emitted a user-message event. If a first-turn session is unusable, create a recorded replacement attempt using retained inputs and reconcile possible effects before continuing.

Related cases: MSG-06, LIF-02, LIF-03 and E2E-04. The prototype recovered from verified runner history; it is not a production Crewroom inbox or ownership implementation.

### 3. Unsupported effort requests are normalized rather than rejected

| Requested model/effort | OMP observation |
| --- | --- |
| `aperture-openai/zai-org/GLM-5.2`, medium | Accepted; reported high |
| `aperture-google/gemini-3.1-pro-preview`, medium | Accepted; reported low |
| `aperture-bedrock-compat/us.anthropic.claude-haiku-4-5-20251001-v1:0`, high | Accepted; no reasoning level reported |

These are three failures of the proposed strict preflight policy, not evidence that OMP's normalization is itself a defect. Crewroom must validate the requested effort against the selected model's supported values and record requested/resolved/observed values separately. An RPC success response does not establish that the requested setting took effect.

Related case: RTE-06. The same principle applies to future fallback and secondary model calls.

## Passing runner contracts

- Unknown model selection is rejected while preserving the previous model.
- Separate coordinator/specialist processes and process groups remain independent; killing one specialist leaves peers responsive.
- A completed checkpoint can reopen in another process with the same session identity and saved history.
- Aborting a held model stream produces an aborted result, then permits another turn. Shell/tool descendant interruption remains untested.
- Local mailbox storage, deduplication within one service lifetime, acknowledgements and passive observation work.
- Pending delivery survives an abrupt mailbox restart. Observer credentials cannot send messages.
- The external four-hop exchange works across heterogeneous API families with specialist and coordinator recovery after verified persistence.
- Synthetic 401 and 403 failures expose errors with bounded requests; one 429 retries the same model and succeeds; malformed/empty output eventually exposes failure. These checks use a bounded test retry configuration, not a production retry-policy certification.

The 57 profile turns produced exactly one local provider request each. This detects extra calls in those short turns; it does not establish that every OMP planning, compaction or large-context path uses the intended model.

## Isolation and reproducibility

The test guard allowed only allocated loopback ports and denied external traffic, other loopback ports and child-process egress. OMP and Relaycast ran under that OS guard. The Python test controller used only the explicitly selected local endpoints; it is not a general-purpose application security boundary.

Each OMP process used synthetic provider configuration, an allowlisted environment, separate working/session directories and disabled native agent tools/extensions. Read access to the user's OMP/credential directories and writes outside the owned test directory were denied. OMP 18.3.1 needed both a separate `PI_CONFIG_DIR` and `PI_CODING_AGENT_DIR`; the latter alone did not isolate its daemon runtime path. The compiled native addon was copied beside a disposable binary to avoid exposing the user's OMP tree.

All owned OMP/mailbox processes exited. Disposable executable/addon copies were removed; logs and synthetic fixture state remain in ignored test output. No live Jira/PR state or production repository was touched. The retired OMP installation remained inactive.

Run everything currently executable with:

```sh
python3 scripts/run-offline-suite.py
```

The command writes its output directory and returns nonzero while any dependency contract fails or full product cases remain unimplemented. Individual entry points are `scripts/test-omp-offline.py`, `scripts/test-mailbox-offline.py` and `scripts/test-omp-offline-faults.py`; each requires a fresh `--output` directory. The current fixtures target this macOS host, installed OMP 18.3.1 and the already installed ignored Relaycast runtime. No dependency installation or catalog refresh is performed.

Development runs exposed two fixture setup mistakes—an absent mailbox data directory and the assumption that Relaycast calls its queued state `pending`. Those were corrected before the final consolidated run. The restart-deduplication, first-turn persistence and effort-policy failures remain reproducible after those corrections.
