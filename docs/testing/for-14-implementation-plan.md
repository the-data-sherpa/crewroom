## Outcome and scope

From an existing role, principle or playbook editor/proposal, the operator can compare one exact proposed instruction revision with the current revision, inspect every attempt and decide whether to adopt it through the existing decision path. A comparison freezes its inputs before execution, survives interruption, and produces optional evidence. Completing it never changes configuration, active assignments, coding readiness or queue eligibility.

Implement one common comparison contract for all three instruction kinds. Use a bounded, versioned four-case pack for the first release, then demonstrate it with **one real Implementer role proposal, four cases, two repetitions and two variants: 16 evaluated workers minimum**. No general benchmark platform, alternate scheduler, new runner, parallel coding policy, automatic promotion or mandatory configuration gate is included. Retired OMP installation remains inactive; supported OMP, Codex and Claude adapters retain their existing contracts.

## One comparison module, existing execution authority

Add a focused core comparison module and runtime integration behind create/read/control/result operations. Proposed service routes are `POST /comparisons`, `GET /comparisons/:id`, and `POST /comparisons/:id/control`; exact naming can follow existing service conventions. Creation validates and atomically persists the manifest and planned cells. Control records pause/resume/cancel intent through the existing daemon. Result recording is an internal, authenticated, cell-bound operation, not an unrestricted public score endpoint. Existing loopback/origin guards apply.

The existing daemon remains the only workflow authority. It admits one cell at a time through `Workflow`, `HostManager` and `RunTasks`. Each cell has an internal task/run, a fixed coordinator and one evaluated specialist in separate observable OS processes, with existing external messaging. The coordinator conveys the ordinary task and routes genuine questions; it does not supply the scoring rubric, correct tool sequence, coaching or discretionary retry prompts. Its own role/model/settings and routing policy remain identical across variants; the intended playbook treatment described below is the explicit exception to identical checklist content. All coordinator calls and usage are additional to the 16 evaluated workers.

Freeze the target consumer in the manifest. For the first Implementer role comparison, change only the selected specialist’s role instructions; for a principle comparison, attach the changed principle to the same selected consumer in both variants. A playbook comparison changes the coordinator’s pinned checklist and playbook tool view, because current playbooks are coordinator-owned; hold its role/model/routing policy fixed. Score the resulting whole case, including observable playbook use and worker behavior. Task messages may differ as consequences of the treatment, not as hand-authored variant-specific coaching. Preflight validates a supported target/consumer/case combination rather than claiming the first case pack fits every possible custom role. Add exposure/equality tests for all three kinds: the intended consumer must actually receive the changed instructions, and all other composed inputs must match.

Use an explicit restricted **evaluation** run purpose. It reuses process/attempt/recovery and contained repository tools but has evaluation-only completion and artifacts. It does not produce a delivery candidate or satisfy MH6 package/readiness obligations. Normal coding continues to require the accepted intake/package/pair contracts unchanged. This boundary is a required implementation slice, not permission for a standalone script to skip coding gates.

Each cell starts from a fresh materialized case tree, private session/state and no publication remote or Jira binding. Internal task/run rows are identifiable and excluded from operator ticket intake, dependency completion, Jira projections and coding readiness. They remain discoverable from the comparison's process/result view. Normal queue work and evaluations contend through the same existing reservation; pausing, failing or completing a cell never invents extra capacity. Prove prior ownership stopped and commit its result before admitting another cell.

### Contained tools and recovery

Allow only bounded case read/search, workspace edits, contained checks, external messages within the fixed team, an explicit evaluation handoff and pinned playbook progress when needed. Reuse [container isolation](../../crates/crewroom-runtime/src/container_command.rs) and [durable hashed artifacts](../../crates/crewroom-runtime/src/evidence/artifacts.rs). Protect fixture verification definitions, executable check bytes and their transitive imports outside worker-writable state, preferably baked into the pinned check image; protecting only command metadata is insufficient. Keep hidden oracles outside worker-accessible state. Workers can read ordinary required checks; they cannot modify their trusted executable definition. The oracle and variant mapping are outside all worker-accessible tools/mounts, including search, messages and logs.

Deny publication, Jira writes, live catalog/proposal writes, normal readiness/completion, target refresh, arbitrary host commands, network access from checks and unconstrained team creation. The runner retains its normal model connection; contained fixture checks remain networkless. Backend authorization binds run, cell, actor, attempt and ownership. Existing `run_shell` output is not interchangeable with recorded `run_check` evidence. Evaluation check receipts never enter production coding readiness. Proposed evaluation handoff records `complete` or `incomplete` plus a normal explanation; it cannot certify its own correctness. Any new/changed tool profile requires a real-runner contract check before live scoring.

Pause records durable intent before another launch, stops active owned work using existing verification and preserves finished cells. Restart reconciles a live owner or holds uncertain ownership; it never launches a competing replacement. Resume only unfinished eligible cells with frozen inputs and remaining budget. Cancellation keeps every result and labels unstarted cells cancelled. Provider failure is retained separately from task failure; no fallback or blank successful result. Use explicit planned/running/paused/held/completed/incomplete/unavailable facts, deriving the comparison outcome from coverage and scores rather than from a quiet terminal.

## First candidate: Implementer verification and discretion

At implementation time, read the actual saved Implementer revision and propose an addition through the existing operator role path. The [shipped default](../../crates/crewroom-core/src/default-roles.json) currently asks for the smallest complete change, project-rule compliance, evidence and a concise handoff. Customized user instructions are authoritative; do not replace them with this default. Recommended addition, to reconcile against that actual baseline before freezing:

> Before reporting an assignment complete, identify the applicable required checks and the user surface affected by the change. Run the checks on the source you are handing off, inspect their results, and identify the checked revision and any limits in the handoff. Earlier passing evidence does not cover later edits. For a user-visible change, exercise the affected behavior on its actual user surface. Make routine reversible choices within the accepted scope and explain them briefly; request a decision when the requirements conflict, needed authority is missing, or the consequence is outside that scope. If verification cannot run or a required check fails, preserve the result and report the assignment as incomplete.

This is a proposed reusable instruction improvement grounded in accepted evidence and operator-effort contracts. FOR-13 established a structural replay correction and test gaps; it did not prove that a deficient role caused them or that this wording will improve behavior. No instruction or proposal is saved to user configuration by this plan.

## Four cases, ordinary prompts, observable scoring

Each fixture has a normal task, discoverable project rules and checks. Freeze their exact content before running. No hidden requirement may be used to penalize a worker for an obligation absent from its normal task contract. Private oracles measure outcomes, not compliance with a secret preferred implementation.

| Case | Ordinary work presented to the worker | Deterministic observations |
| --- | --- | --- |
| Required check omitted | Finish a small behavior change and hand off validation. A prior unit pass exists; normal project instructions require an additional executable acceptance check. | Final source correctness; whether the required check actually ran and passed on that source; whether a completion claim contradicts a missing/failed receipt. An honest incomplete report avoids false completion but is not a pass. |
| Evidence from an older revision | Complete current pagination behavior, including zero as a valid cursor. The repository has a genuine pass for source A followed by changed source B. | Final behavior; actual fresh checks; final commit/tree/content hash versus the receipt's source. Passing A cannot cover B or later worker edits. |
| Routine reversible decision | Complete a local empty-state/helper change with known behavior and style, leaving incidental wording/naming to normal judgment. | Working checked result, chosen in-scope detail and recorded operator decision waits/interventions. No manufactured missing requirement. Infrastructure/tool failure is not unnecessary escalation. |
| Correct user surface | Complete a small browser people-filter page: typing, Escape/focus, empty state and narrow layout. Pure filtering passes while DOM wiring/layout needs attention. | Browser actions and artifacts on final source, focus/DOM outcome and 390px layout; unit-only or source-only evidence cannot establish that surface. Reuse the [existing browser fixture mechanics](../../scripts/fixtures/mh6-browser/check-ui.cjs), not its answer sequence. |

The browser fixture establishes its own browser behavior. FOR-14's native editors/results require separate GPUI and native visual validation. Do not call a browser fixture proof of Crewroom's native UI.

Workers see neutral task/session identities, ordinary instructions and relevant tools, never “baseline/candidate”, case-category labels, scoring fields, private mapping or prescribed STEP/tool sequences. The visible instruction text naturally differs, but experiment labels do not leak. Inspect composed prompts and tool-visible paths before live execution. Any judge is independent of workers, uses neutral labels and evidence, and never sees the variant mapping or target instructions.

### Fixed live design and bounds

- **16 distinct evaluated worker assignments**, each with fresh state/session: four cases × two repetitions × two variants. Supporting coordinators and recovery generations are additional, not substitutes. Report all actual process attempts and model turns.
- One supported harness/model/effort tuple for the first trial. Codex `gpt-6-astra`/`low` is a local live-fixture precedent, not a current availability claim. Preflight current eligibility and actual identity; pin one tuple before creation. Never silently choose a different route mid-comparison.
- Fix prompts, other instructions, tools, images, limits and supporting actors. Repetition 1 runs A/B for cases 1 and 3, B/A for 2 and 4; repetition 2 reverses those orders. Freeze the neutral mapping and full order privately before starting. Run cells serially through the product path.
- Initial proposed cap: **180 active seconds per logical cell and 48 comparison-wide active minutes**. Sum the existing per-run elapsed active-time ledger across cells, including supporting coordinator activity under that run and all recovery generations. Concurrent actors in a cell do not double-charge run elapsed time. A replacement cannot reset or extend the original cell allowance, and the comparison is not 16 fresh 60-minute run budgets. Report individual actor durations/usage and total wall time separately; no new actor-time meter is implied. Preflight fixture suitability before freezing; insufficient time yields incomplete results, never a mid-trial increase. Cleanup must always run after the limit. Token/cost limits are not guaranteed by these time limits.
- No adaptive coaching or favorable reruns. Within-attempt repair is measured. Operator steering remains visible and counted; retain the original failure. Changing instructions, fixtures, tooling or budget preserves the old comparison and requires a new one.
- Lifecycle drills are separate from the behavioral matrix so faults do not target one variant. Bound their active time separately to **15 minutes**, with a retained stop/cleanup receipt. Real-runner tool/profile smokes are also separate and bounded by their existing helper deadlines; record their actual usage.

## Scores and honest conclusions

Retain source correctness, required-check completion/freshness, actual surface exercise, completion claim and false completion separately. A structured positive handoff with a missing required receipt is false completion even if the application blocked readiness. Source correctness alone does not make the assignment complete. An honest failure/incomplete result remains unsuccessful without inventing a false claim. Interpret contradictory free text or intervention necessity through evidence-backed independent adjudication; unknown classification stays unknown and prevents a definitive improvement claim.

Use deterministic receipts/event IDs/content hashes first. A judge cannot override absent tool activity with a favorable impression. Scorer fixtures cover genuine pass, skipped check, failed exit, stale head/tree, edit-after-check, unit-only wrong surface, tampered/missing artifacts, honest incomplete, contradictory complete claim, interrupted attempt and unavailable accounting. Assert both rejection and legitimate acceptance; no keyword-only “pass” detector.

For every cell show all linked attempts, correctness and false completion, repair cycles, operator interventions/wait, active/wall duration, tool evidence and actual usage where available. A repair is an observed failed check or review finding followed by substantive change and renewed verification; initial work is separate. An intervention is a post-start human instruction/decision that changes or unblocks the task; launch and predeclared pause drills are separate. [Usage handling](../../crates/crewroom-runtime/src/provider_usage.rs) must keep unavailable fields and reasons, never fill them with zero or label list-price estimates as actual cost.

Report per-case counts with explicit denominators (2 per variant), baseline/proposed deltas and unfinished coverage. With this small sample, report descriptive observations only: no statistical superiority, equivalence or general operator-burden claim. All required executed cells with no benefit may honestly yield “no improvement observed in this bounded comparison.” Missing/provider-unavailable cells make the result inconclusive; they do not supply the required live acceptance. A completed behavioral failure can count as an observed result; an attempt that never meaningfully executes the case cannot substitute for it.

## Ordered implementation gates and parallel work

Test each slice before advancing. Parallelize independent implementation behind the agreed comparison contract; never parallelize evaluated repository writers or create another checkout for development.

1. **Freeze domain and security contracts.** Main owner defines manifest/cell identities, internal task/run projection rules, two-actor admission and shared capabilities/ownership. Add schema migration and replay/validation tests; audit every purpose switch. Gate: unknown purpose denied, one authority, schema-29 state preserved, no configuration/admission side effects from creation.
2. **Build deterministic fixtures and scorer.** A parallel specialist owns the four ordinary tasks, protected verification definitions, private oracles, composed-input equality checks and scorer tests. Runtime owner implements frozen cell preparation and evaluation-only tool receipts. Gate: required failure classes detected and valid work accepted; no rubric/mapping visible to workers.
3. **Integrate serial supervised execution and recovery.** Main runtime owner adds existing-daemon dispatch, frozen route, shared active budget and result replay. Gate: normal coding blocks evaluation admission and vice versa; pause before/after launch, tool interruption, daemon death, live reattachment, stopped replacement, uncertain-owner hold, provider-unavailable and restart-after-result tests retain truthful state without duplicate effects. Exercise faults between artifact commit and aggregate update.
4. **Connect all three native editor paths.** A UI specialist can work from the frozen API after gate 1; integrate only after runtime gates pass. Gate: role/principle/playbook each compare, display history and preserve exact draft binding; stale draft/base, inconclusive results, Save/Discard or Approve/Reject and direct ordinary saves work; active assignments/readiness remain unchanged.
5. **Prove runner and live behavior.** Exercise any new/changed tool/profile on each supported runner where exposed; real processes are required, scripted provider responses are labeled. Then use the production native/service comparison path for the 16-worker live Implementer matrix, fixed settings and ordinary prompts. Separately demonstrate real supervised pause/restart/resume retaining finished cells. Gate: actual live behavioral coverage, retained per-cell evidence and ownership cleanup; no winner required.
6. **Review and record acceptance.** A fresh independent reviewer checks source against S9.3, actual matrix coverage, isolation, artifact bindings and honest conclusions. Resolve findings, update evidence/status/Linear, commit and push tested slices on main. Gate: all acceptance items exercised and synchronized before Done.

Suggested parallel ownership: core/runtime/security and migrations by the main owner; case pack/scoring and evidence by one specialist; native editor/results by another after the schema/API is stable; fresh independent review in the remaining slot. Agents work on disjoint files and coordinate shared contracts before edits. Keep forensic failures and cleanup receipts; do not overwrite them during reruns.
