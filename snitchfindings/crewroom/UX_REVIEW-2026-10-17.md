## Ethics gate

**Pass.** This is a single-operator working tool. No surface uses urgency, scarcity, social proof, a hidden charge or a re-asked consent. The one cost disclosure was checked: the comparison preflight states "16 evaluated workers" and "Model usage can incur charges" before Start (`comparisons.rs:329-331`). Exits use neutral labels ("Keep run", "Keep editing", "Keep repository"). Claim truth needs no business-fact Skip; the product claims are about internal state.

## Findings

Severity follows the snitch-ux rubric. "Source" confidence means the branch is certain in code and the runtime frequency is unverified.

### High

#### H1. Unsaved new and duplicated drafts become unreachable, though the copy promises they are kept
- **Surface:** `workbench/settings/roles.rs:11-25`, `:341`, `:353`; `settings/principles.rs:59`, `:179-182`; `settings/playbooks.rs` (Create playbook); `settings.rs:216-226`
- **Evidence:** Create and Duplicate store each draft under a fresh key (`format!("{NEW}-{}", uuid::Uuid::new_v4())`). Catalog cards open only saved items, and no code lists the draft maps. The editor says "Drafts stay here when you switch roles or pages." and "Close editor · keep draft". Duplicates set `draft.original = Value::Null` (`roles.rs:22`), so they stay dirty, and `unsaved()` scans every draft, so the close guard warns about drafts the operator cannot open.
- **Principle:** Copy must match behavior; a draft must stay where the copy says it is.
- **Risk:** The operator writes role instructions, switches as invited, and loses the work. A later close warning about invisible drafts erodes trust in the guard.
- **Fix:** List unsaved new drafts at the top of each catalog as "Unsaved draft · {name or Untitled}" with Open and Discard, or reuse one fixed new-draft key per section as Repositories does. Give an untouched duplicate a baseline. If neither ships, label the button "Close · discard new draft" and confirm.
- **Verify:** Create role → type a name → Edit another role → reopen the draft. Duplicate, close untouched → window close shows no unsaved-work dialog.
- **Severity:** High
- **Confidence:** High (source); runtime not rendered.

#### H2. Accepting a plan also replaces the accepted brief and criteria without saying so at the button
- **Surface:** `workbench/intake.rs:153`, `:590-601`; core `intake/mod.rs:149-150`
- **Evidence:** When the plan has `requirements`, accept calls `s.accept_requirements(...)` and bumps the task revision. The hint beside Accept says "Accepting saves the plan. Queue remains a separate action." The only disclosure is a card heading, "Requirements adopted with acceptance", which also appears on rejected and historical plans. The plan editor carries `requirements` forward but never shows them.
- **Principle:** Disclose the consequence at the point of commitment.
- **Risk:** The operator accepts a plan and silently changes the requirements every later check and review is judged against.
- **Fix:** When `plan.requirements` exists, render beside Accept: "Accepting also replaces your accepted brief and {n} criteria with this plan's proposed requirements (revision {r} → {r+1})." Show current and proposed side by side. Title the card section "Proposed requirements" unless `decision == accept`.
- **Verify:** Ask an operator what changes when they accept such a plan; closed when they name the brief change before clicking.
- **Severity:** High
- **Confidence:** Medium; artifact High, judgment Medium because the heading partly discloses it.

#### H3. PR delivery says "Ready for human review" from a stale record, beside "Validation incomplete"
- **Surface:** `workbench/results/publication.rs:33-41` vs `results.rs:152-156`, `:170-174`; `observation.rs:32-35`, `:50`
- **Evidence:** The Results headline requires `self.observation.result_fresh`. The PR headline uses only `record["ready"] == true`. A disconnect sets `result_fresh = false` but keeps the record, so one screen can show "Evidence observation is not current. Retained records may be stale.", "Validation incomplete" and "Ready for human review".
- **Principle:** State must be true at the decision point; evidence must not overstate how current it is.
- **Risk:** At the merge decision the operator trusts the stronger, out-of-date verdict.
- **Fix:** Gate the PR headline on `result_fresh`. When stale: "Last observed ready for human review · observation not current. Reconnect before relying on this." Same for "Last observed merged".
- **Verify:** Journey test with `observation.disconnected()` and a ready record; no "Ready for human review" text renders.
- **Severity:** High
- **Confidence:** Medium; source High, runtime frequency untested.

#### H4. The agent wall says no agents exist while it is still loading or cannot reach the service
- **Surface:** `wall.rs:279-286`, `:296-306`, `:651-656`, `:661`
- **Evidence:** A new wall starts with `runtime: Value::Null` and an empty `error`. The body renders "No current agent processes. Queued plans are not executing agents." and the status reads the normal "Read-only observation…" until the first snapshot. If the first fetch fails, the body still says no agents exist.
- **Principle:** Loading and unavailable states must differ from empty.
- **Risk:** The operator checks whether agents are running, is told none are, and may cancel or re-queue a healthy run.
- **Fix:** Until a snapshot arrives: "Loading agents for this run…". On first-fetch failure: "Agent observation unavailable: {error}. This does not show whether agents are running." Show the empty copy only after a successful snapshot.
- **Verify:** Point the wall at a stopped and a slow service; "No current agent processes" never appears. UI test rendering before any snapshot asserts `wall-empty` is absent.
- **Severity:** High
- **Confidence:** Medium; source High, how long the state lasts depends on service latency.

#### H5. Agent state labels hide "needs attention": grey "Recorded" in the panel, raw tokens on the wall
- **Surface:** `workbench/agents.rs:198-205`; `wall.rs:598-614`, `:635-644`; core `observations.rs:149`, `attempts.rs:226`, `:296-300`
- Merged instances (one shared state-label mapping fixes both):
  - Agents panel: the match covers executing, idle, admitted, exited and failed; `_ => (0x9eacb9, "Recorded")`. Core sets `attention_required` on process exit and `starting` on start, so both render as neutral grey "Recorded".
  - Wall: prints the stored token ("Reviewer · attention_required · ownership unconfirmed"), never reads `ownershipReason`, and pairs `admitted` with "Assignment has no admitted terminal process." Bare "idle" sits next to a quiet terminal.
- **Principle:** Agent activity is a separate, readable fact; a quiet terminal is not a quality gate.
- **Risk:** The operator cannot tell a dead agent from a healthy or never-started one, and waits on, or steers, an agent that will not respond.
- **Fix:** One mapping used by both: admitted → "Not started"; starting → "Starting"; executing → "Working"; idle → "Waiting · not a check result"; exited → "Stopped"; attention_required → "Needs attention: {ownershipReason}" in the warning tone; failed → "Failed: {reason}"; unknown → "State: {raw}".
- **Verify:** UI test over every state value asserts the label and, for `attention_required`, the reason text.
- **Severity:** High
- **Confidence:** High (source).

### Medium

#### M1. The generic "Saved on this machine." notice misreports reconcile, delete and decision outcomes
- **Surface:** `workbench.rs:336-343`; triggers at `results/publication.rs:277-289`, `:327-334`, `needs.rs:265-276`, `settings/principles.rs:187-191`, plan decisions in `intake.rs`
- Merged instances:
  - Reconcile publication / Reconcile Jira call the service, which may push, create a PR or read Bitbucket/Jira (`crewroom-service/src/routes.rs:61-75`). Success says "Saved on this machine."
  - Deleting a principle says "Saved on this machine."
  - Accepting or rejecting a plan says "Saved on this machine."; the card header then reads "Plan 2 · accept" (`intake.rs:524-528`).
- **Principle:** Feedback must state what happened; uncertain provider outcomes must be shown accurately.
- **Risk:** The operator reads "Saved" after a reconcile and assumes the uncertain outcome was resolved.
- **Fix:** Path-specific notices: "Publication reconciliation finished. Check push and PR receipts above."; "Jira reconciliation finished. Only confirmed updates have receipts."; "Principle deleted. Existing assignments keep their copied text."; "Plan {v} accepted." / "Plan {v} rejected." Header: "Plan 2 · Accepted".
- **Verify:** Tests that each path yields its own notice and never "Saved on this machine."
- **Severity:** Medium
- **Confidence:** High (source).

#### M2. Save and send results appear far from the control that caused them
- **Surface:** `workbench.rs:900-919` (banner/notice at top of `main`), `:983-999` (separate drawer column); composer `collaboration/conversation.rs:246-264`; Save rows `settings.rs:548`, `roles.rs:517`, `principles.rs:160`
- Merged instances:
  - Steering failures ("…this instruction was not saved.") render at the top of the session column; the composer just re-enables.
  - Long settings forms put Save at the bottom; errors and "Saving…" render at the top. No `scroll_to`/`ScrollHandle` use exists outside tests.
  - At ≥1100px, Brief/Results/History actions live in the drawer, but their errors render in the other column.
- **Principle:** Show failure next to the action, persistently.
- **Risk:** The operator clicks Save or Send, sees no change, and assumes success or retries blindly.
- **Fix:** Render the current error/notice directly above the action row that produced it (composer, Save row, drawer top). Example: "Not stored: {reason}. Your text is still here."
- **Verify:** Scroll to a repository Save, submit a bad digest; the error is visible without scrolling. Same for a forced 409 on steering.
- **Severity:** Medium
- **Confidence:** Medium; layout not rendered.

#### M3. Notices and errors follow the operator to unrelated tickets and panels
- **Surface:** `workbench.rs:900-919`; cleared only at `:344`, `:483`, `:518`; navigation handlers `shell.rs:158-163`, `:252-257`, `:328-331`, `needs.rs:26-33`
- **Evidence:** No navigation handler clears `notice` or `error`; both render atop every panel.
- **Principle:** Feedback stays attached to its source.
- **Risk:** After a failed save on ticket A, ticket B shows A's red banner, and the operator attributes it to B.
- **Fix:** Store the panel and task each notice belongs to; render it only there. Keep `connection_error` global.
- **Verify:** Error on A, select B: no banner; return to A: banner present.
- **Severity:** Medium
- **Confidence:** High (source).

#### M4. Disabled decision and recovery controls rarely say why
- **Surface:** `intake.rs:61-66`, `:125-129`, `:141-146`, `:515`; `planning.rs:85`; `refinement.rs:166-171`; `results/publication.rs:281-285`, `:329-331`; `results/recovery.rs:148`; `collaboration/learning.rs:119`, `:129`
- Merged instances:
  - Stale-basis hint says "Refresh the repository basis…", but that button is disabled when `needsReacceptance`; the real first step, Save brief, is at the top of the tab.
  - Accept plan, Save plan draft, "Use repository", Adopt revision: disabled with no stated reason.
  - Reconcile publication and Refresh/Retry from target: disabled on unavailable connection or stale runtime; the Results tab never says so.
  - Learning Approve/Reject disabled until a reason is typed; label is only "Decision reason".
- **Principle:** Name what blocks a disabled control and what clears it.
- **Risk:** The operator follows on-screen guidance into a dead control, or guesses which step is missing.
- **Fix:** Reuse the existing "To queue: …" pattern (`planning.rs:175-177`) per area, e.g. "To decide: save or discard brief changes · answer open questions"; "To reconcile: Bitbucket connection unavailable for this repository". When `needsReacceptance`: "Save the brief to accept the changed Jira requirements, then save a new plan version." Label "Decision reason (required)".
- **Verify:** Each disabling condition renders its hint (unit test). Jira-change → plan-review task: nobody clicks a disabled control first.
- **Severity:** Medium
- **Confidence:** High (source).

#### M5. Three irreversible actions run on one click, unlike Cancel run
- **Surface:** `collaboration/refinement.rs:90-92`; `comparisons.rs:410-435`; `planning.rs:388-393`
- Merged instances (one fix: reuse the `run_actions.rs:156-159` cancel dialog):
  - "Close refinement run" posts `/runs/{id}/close` immediately; the run cannot reopen.
  - "Cancel remaining cells" sits beside Pause; `cancelled` is terminal, so continuing means paying for a new comparison.
  - "Remove queued plan" cancels the run (`store.rs:579-586`), and the notice says "cancelled". The server only allows unadmitted plans with no agents, so no running work is lost, but the plan cannot resume and loses its queue position. "Remove" reads as reversible list editing.
- **Principle:** The guard matches how reversible the action is.
- **Risk:** A slip next to an adjacent control (Pause, Move down) ends work that cannot be resumed.
- **Fix:** Confirm each: "Close this refinement run? The agent stops. Proposals and notes are kept." / "Cancel remaining cells? {k} of {n} cells can't be resumed. Finished results are kept." / rename "Cancel queued plan…": "It leaves the queue and cannot resume. Queue it again from the Brief." Buttons "Keep running" / "Keep plan".
- **Verify:** Each control opens a dialog; the keep option leaves state unchanged (GPUI test, `cancel-run` pattern).
- **Severity:** Medium
- **Confidence:** High (source).

#### M6. Before the first workspace load, the shell says integrations are unconfigured and nothing is queued
- **Surface:** `workbench.rs:205`; `needs.rs:316-321`; `shell.rs:234-235`, `:261-263`; `settings.rs:263-284`
- **Evidence:** With `workspace: json!({})`, Needs you says "The workflow service is running without its execution layer…", the sidebar says "No queued plans.", and the footer says "Jira not configured · Runner not configured".
- **Principle:** Show loading and offline states as such, not as empty or unconfigured.
- **Risk:** With the service down or starting, the operator edits configuration or concludes the queue was lost.
- **Fix:** Track `workspace_loaded`; until true, one message: "Waiting for the workflow service. Tickets, queue and decisions appear once it connects."
- **Verify:** GPUI test with no service: none of "execution layer", "not configured", "No queued plans" render.
- **Severity:** Medium
- **Confidence:** High (source).

#### M7. "Validation pending or blocked" covers push and PR delivery failures
- **Surface:** `results/publication.rs:38-47`; runtime `publication/dispatch.rs:100`, `:126`, `:220`, `:235`, `:324`
- **Evidence:** Any non-merged, non-ready record shows that headline, with raw "Push: {} · PR: {}". Push `blocked` (remote moved), `uncertain` (outcome unknown) and PR `blocked` (open PR exists) are not validation results.
- **Principle:** State integration outcomes accurately, in the operator's words.
- **Risk:** The operator waits for checks instead of reconciling or inspecting the remote branch.
- **Fix:** Headline from receipts: "Push outcome unknown · reconcile to confirm" / "Push blocked · remote branch changed" / "PR blocked · another open PR exists" / "Publishing · receipts pending" / "PR created · hosted validation pending".
- **Verify:** Unit test maps each push/PR state pair to a distinct headline.
- **Severity:** Medium
- **Confidence:** High (source).

#### M8. "Plan queued" notice is wrong when Queue starts scoping
- **Surface:** `workbench.rs:383-385`; core `store.rs:450-454`, `intake/requests.rs:103-126`
- **Evidence:** With no accepted plan, queueing creates a `grill` scoping run, but the notice says "Plan queued. Execution waits for a saved launch team and an available coding slot."

- **Risk:** The operator expects coding to start; a coordinator scoping run is what waits.

#### M9. "Request revision" on an operator-written plan revises nothing

- **Risk:** The operator waits for a revision that no agent will produce.

#### M14. Plan editor validation names neither the field nor the package, and fires on a pristine editor

#### M15. Repository save errors don't identify the check or field
- **Surface:** `settings.rs:459`, `:467-470`, `:137-149`; core `repositories.rs:19`, `:111`, `:122`, `:128`, `:146`, `:246`
- **Evidence:** A tag like `alpine:3.20` fails the length test first: "image must contain 71–71 characters." The clear digest message is unreachable for wrong-length input. Others: "timeoutMs must be an integer between 100 and 3600000.", "Invalid targetBranch.", and one message for both a bad path and a bad branch. None names which check.

- **Verify:** Two checks, check 2 with a tag and check 1 with timeout 50: each message names its check and field.
- **Severity:** Medium
- **Confidence:** High (source).
