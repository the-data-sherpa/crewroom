Named features → existing case IDs

The three acceptance journeys

01 · Steering across reconnect

UI-02 · relevant E2E-05 steps

Select ticket → Conversation → send while coordinator delivery is held → reconnect → release delivery → observe received → record applied disposition.

Compare the same message ID, body and transition times in native UI and durable records. Reconnect must not duplicate the instruction or its application.

Gap to close: existing native reconnect tests retain pending steering; receipt/application must be joined through the authenticated fixture tool.

02 · Pause/resume

UI-04 · LIF-05 · Resume subset of LIF-06 · relevant E2E-05 steps

Start bounded active work → native Pause → pausing while ownership is unstopped → confirmed paused → reopen → native Resume → retain history and stop owned resources.

Reuse existing ownership checks. Current attempt and process identities must agree; no old and new writers execute together.

Gap to close: narrow the current control gate and retain the intermediate state without making specialist insertion or PR feedback mandatory.

03 · Readiness invalidation after a revision change

EVD-04 · revision-drift subset of E2E-09

Establish a ready fixture candidate with real checks and independent scripted review → advance the isolated target → native Refresh target → observe changed revision and false readiness.

Retain old candidates, checks and review as history. No automatic execution follows. The recipe ends at proven invalidation.

Gap to close: prove the initial ready state. A fixture that was never ready cannot establish ready → invalid.

These cover named case subsets. They do not certify all of E2E-05/E2E-09, cancellation, target conflicts or hosted CI regression.

Ordered implementation

Seven gates before completion

1 · Bind scope and discovery

Create docs/testing/feature-map/ with an index, three unverified recipes and a manifest referencing existing case IDs, entry points and fingerprints.

Gate: each feature resolves to one bounded recipe and its accepted case subset.

2 · Add a narrow versioned helper

Proposed scripts/verify-feature.py exposes list, check, run and ownership-checked cleanup. It selects one journey, retains evidence and rejects missing prerequisites, stale entries and zero tests.

# Proposed interface — not implemented
python3 scripts/verify-feature.py check steering-reconnect
python3 scripts/verify-feature.py run steering-reconnect --evidence-dir <new-directory>

Gate: guard checks reject false passes and foreign cleanup targets.

3 · Join steering input, reconnect and disposition

Extend existing native actions and fixture latches. Capture stored, received and applied separately through the actual authenticated fixture path.

Gate: one instruction keeps its identity across reconnect and native readback.

4 · Document and exercise Pause/Resume

Reuse the native control driver and owned process observations; expose a focused command and exact operator steps.

Gate: stopped ownership precedes paused; explicit Resume retains history.

5 · Establish ready → invalid

Reuse the current ready-candidate/check/review fixture and native target refresh. Record source identities before and after the nonconflicting target change.

Gate: the UI and durable assessment both reject the old evidence for the changed candidate.

6 · Run from the feature name, then break a recipe reference

Add the index pointer to normal project context. Give a fresh specialist the feature name and checkout, with no private coaching. Missing instructions are recipe defects.

Change one selector in a disposable manifest copy. Detect stale selection before launch, correct it, then rerun that recipe on the native surface.

Gate: three discoverable executions plus one demonstrated stale detection/correction.

7 · Record final checks, limitations and cleanup

Run changed-code gates, review the diff and acceptance receipts, update status/progress and Linear with exact commits. Mark Done only when all FOR-12 acceptance items are satisfied.

Gate: verified Linear readback and retained source-bound evidence.

Testing scope

What belongs in FOR-12

Select a category to inspect its boundary. These filters change only this view.

  • RequiredThree native recipes + one stale correction rerun. Fresh specialist, isolated state, actual GPUI actions, durable outcomes and checked cleanup.
  • RequiredFocused helper guards. Unavailable prerequisite, stale selector, zero tests, wrong binary, interrupted retention and foreign-resource cleanup refusal.
  • RequiredHonest evidence. Exact recipe/source/binary identity and platform. Scripted provider results stay distinct from live delivery.
  • If code changesRust driver changes: format, workspace/example builds as used, focused desktop tests and affected native recipes.
  • If code changesRepository gates: domain → npm test; type/build → npm run build; user-flow changes → npm run test:e2e. Production Rust changes require scope review and affected Rust checks.

  • Outside scopeMutation trials and instruction comparisons. These belong to FOR-13 and FOR-14.

Bounded diagnosis

Rerun for a reason. Stop with evidence.

Proposed implementation-time rules
TriggerRequired response
Missing prerequisiteRecord unavailable/incomplete before launch. No silent install, credential refresh, browser substitution or skipped-action pass.
Failed journeyRetain logs and classify: recipe, helper, environment, product or ownership. State a hypothesis before retrying.
Recipe/helper repairRerun affected recipes only. Shared helper changes require all affected recipes. Documentation-only receipt updates do not trigger full application suites.
Two unsuccessful rerunsStop that failure lane. Report attempts and next bounded action. Further runs require new evidence or a revised testing decision.
Unclear ownershipKeep the result incomplete. Stop only resources whose recorded identity belongs to the verification run.
Production redesign neededRecord the blocking acceptance item and a CrewRoom follow-up; resolve scope before expanding implementation.

The expected completion matrix is three accepted recipes plus one corrected stale-recipe rerun. Diagnostic failures remain in the record; the count never waives missing acceptance.

A pass must be attributable

Keep four kinds of identity separate

Recipe and helper

Commit, content hash, case subset, selected entry point, command and expected/actual test count.

Application and platform

Source commit/diff, binary hashes, OS/architecture, native harness/display mode and tool versions.

Fixture and observed work

Run/message/candidate IDs, Git head/base/tree, native actions, durable snapshots and provider provenance.

Result and cleanup

Exit/timeout/assertions, retained artifact hashes, owned resource identities and confirmed stopped state.

A changed recipe or relevant helper is unverified until re-exercised. GPUI harness interaction proves the native journey; it does not certify OS input or a packaged release.
